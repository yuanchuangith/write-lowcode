# 排查交接、错误修正与编译准备优化

本轮合成冷、热路径与错误修正数据见 [性能报告](optimization-performance-report.md)，可用 `scripts/benchmark_edit_pipeline.py` 复现。

本轮源码改动连接 `look` 的只读定位与 `write` 的受控编辑，减少重复定位、无效编译和恢复环境的工作。全量仍是默认生成模式，增量／自动选择规则、独立生成复验、完整候选 C# 编译及人工 SQL 审批继续保留。

## 接口与调用顺序

| 接口 | 新增能力 |
| --- | --- |
| 只读 `export_edit_handoff(identifier, targets, change_spec, diagnosis_source)` | 集中核对当前草稿和诊断使用的当前副本；本机保存最多 10 个精确节点的参数、定位、控制上下文、原始要求、拟改内容、保留项及场景，返回 `handoff_ref`。 |
| 只读 `read_edit_handoff(handoff_id="", identifier="", sha256="", target_index=null)` | 按编号读取或按精确动作列出候选；必须明确选择，支持同机新对话和有界续读。 |
| 编辑 `begin_edit_session(..., handoff_ref=null)` | 可选导入交接；占用前核对环境、动作、草稿及目标。匹配后直接返回目标 `edit_context`；失效或发布／草稿差异返回定点补查信息。 |
| 编辑 `inspect_edit_context(..., operation_cursor=0, include_context=null)` | 第一页返回完整上下文；后续模板页默认只返回本页精确原值守卫。`include_context=true` 可取完整上下文，`false` 可主动精简。 |
| 编辑 `plan_canvas_patch(...)` | 内部先预检全部操作；返回结构化批次问题，依赖原生结果的检查明确列为待检查。 |
| 两端 MCP 响应 | 外层返回 `trace_id`、总耗时和分阶段 `timings`，失败保留已完成耗时。 |

通常流程为：只读诊断及具体方案确认 → 导出交接 → 显式启用编辑技能 → 建立本对话身份并导入 → 使用已返回模板构造操作 → 一次规划同一草稿的全部已确认修改 → 完整检查及审批。没有交接参数时保持普通定点核对流程。

交接只保存本机设计证据，不继承旧编辑会话、计划或审批。跨对话需确认当前修改范围；本对话已有有效确认则不重复索要。读端不会因为交接记录自动调用编辑工具，编辑端的显式技能启用门禁保持。交接不可用不会留下新占用，不要求重启。发布和草稿差异单独核对，禁止用发布参数直接覆盖草稿。

## 错误后继续

失败响应外层包含 `failure_stage`、`error_code`；`error_details.issues[].context_ref` 提供经基线身份核对的定点读取参数。节点无法映射时只给分组。每次最多返回 20 项独立错误，修正后整批重交以获得剩余问题；完整原值通过上下文读取，不在错误里静默截断。

整批预检先发现字段、路径、目标、原值和别名等便宜错误，不必等待 C# 编译。独立问题集中返回；依赖前面原生结构操作的问题延后到原生编译，不猜生成结果。

修正时复用原始需求、保留项、场景和仍有效的位置证据，按照 `error_details.refresh_scope` 补查。完整重交修正批次；每次从不可变会话基线计算，不把失败候选叠加，也不自动批准旧计划。预检不是原生生成或运行验证通过的证明。

已确认要求在本机会话状态中独立记录并绑定原始草稿和编译器，候选文件损坏或删除不会丢失要求。规划失败仍保留这些要求；要求变更后旧计划不可进入审批，规划登记和审批创建都执行原子比较守卫。旧版本会话若既没有独立记录、候选又已损坏，会返回 `legacy_review_spec_unavailable` 及取消／新建的明确路径，不猜测或清空旧要求。

同对话、同草稿、同模式、同队列的重复 `begin_edit_session` 核对基线、关系、编译器和归属后返回原会话及下一步，不新建备份或打开取消窗口。跨对话接手规则保持。

审批和计划报告窗口以可见回执及主线程心跳判断状态。计划报告使用稳定快照去重，不能将 Popen 成功当作窗口已打开。显式 `reopen_approval` 对失联的单动作窗口，核对启动编号、实际 UI 进程创建身份，在执行锁内重新核对未执行状态后才停止并重开；不释放会话、不产生审批或业务写入。队列暂不强制停止，避免漏锁新入队动作。首屏展示不等待注册表标题加载，损坏的未执行队列候选单独隔离并可重试，结果不明的执行仍停止。

## 缓存边界与耗时解释

注册表／元件契约采用有界进程内缓存，按内容和执行环境绑定；Git 来源状态刷新，正式生成和独立复验仍启动新的 Node。缓存的是规则准备，不是候选检查结果。

C# 工作区按实际 SDK、框架、DLL 内容及项目／NuGet 模板绑定，通过跨进程独占槽复用 restore。冷环境先 restore，冷热路径均执行完整的 `dotnet build --no-restore --no-incremental`；规划和审批分别编译，DLL 前后指纹核对、探测进程、超时和子进程树清理保持。损坏或中断工作区不提供旧成功，候选源码与输出不会串到其他检查。

普通 Candidate.cs 的纯 `CSxxxx` 代码错误，经引用和 restore 元数据复核并清理候选输出后可保留 restore；混合错误、工具／环境错误、漂移及中断仍使缓存失效。每次修正仍实际完整 build。相邻的注册表和编译器绑定读取共享当次内容核验，各独立 Node 命令仍前后扫描源码、bridge 和 adapter，不缓存候选通过结论。

`timings` 记录数据库、交接、预检、规则、生成、复验、引用、SDK、restore、build 和业务复核阶段；模型思考和网络往返需要另行测量。计时不进入业务内容指纹或审批签名，日志不写参数、代码、凭据。以小改、大改和错误修正的冷／热实测报告评估，不从缓存命中推断整体提速比例。

这是两个仓库的源码交付。没有自动安装、升级、切换运行版本、重启 Codex、保存或发布业务草稿。工具字段和操作细节见 [技能参考](../skills/gxp-lowcode-edit/references/evidence-and-performance.md)；已有历史数据见 [生成测量](generation-quality-and-speed.md)。
