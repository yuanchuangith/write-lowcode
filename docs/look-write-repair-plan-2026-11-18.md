# Look / Write 提速与编排可读性修复计划

这份计划以 Look 和 Write 的当前源码、2026-11-18 指定对话的耗时记录，以及截图中的「默认带入修订人」为依据。目标是减少重复取证，让新生成的画布能直接看出业务判断，且不改变原有执行结果。本文只提出计划，未改插件代码或业务草稿。

| 顺序 | 范围 | 交付结果 |
|---|---|---|
| 第一批，可并行 | Look 表结构查询；Write 交接校验 | 已知表名不触发全库扫描；交接按正确的动作身份复用 |
| 第二批，可并行 | Look 批量取证；Write 画布质量检查 | 一次读取目标节点和所需字段；复杂逻辑不能只换个容器，要求的注释能在画布上看到 |
| 第三批 | 跨仓库回归和真实画布验收 | 用相同任务测前后差异，先验收修订人规则，再分批整理存量编排 |

## 第一批：修掉已经证实的卡点

1. **Look：把表名查找与整库关系刷新分开。** 已知表名直接 `describe_table`，现有实现只查列和索引。模糊搜表、字段或备注时，优先查现成目录索引；缓存缺失时走有返回上限的只读元数据查询。需要可信跨表关系时才走原有验证流程；旧缓存标明时间，未验证的关系不能当成事实。将表快照改为短文件名，按索引继续读取已有缓存；复用 Windows 长路径处理，保留同卷原子替换和最后一份有效快照。刷新失败后回退到窄查询，短时间内不重复触发同样的全量刷新。验收：Windows 下复现 262 字符旧路径场景并验证新写法成功；兼容已有索引；并发和写入失败时保留旧快照；精确表名和冷缓存模糊搜索均不跑全库关系刷新。入口：`look/mcp/gxp_core/schema_snapshot.py:401`、`look/mcp/gxp_core/repository.py:687`；测试扩展 `look/tests/test_schema_snapshot.py`。

2. **Write：用同一套动作身份校验交接和建立会话。** Look 导出的是元数据里的业务动作编号，Write 的交接校验却拿它和草稿行自身的 `code` 比。本次 RefId 相同、业务动作编号为 `ACP81z9m`，仍报 `HANDOFF_TARGET`。让交接发现、导入及会话统一采用规范动作身份；草稿行标识照常独立核对。继续检查环境、RefId、草稿和节点指纹，只有变化的目标需要重新核对。验收：业务编号与草稿行 `code` 不同但指纹匹配时可复用；跨环境、错 RefId、错动作仍拒绝；草稿漂移只能作为线索，不能直接套用旧值。入口：`look/mcp/gxp_core/edit_handoff.py:103`、`write/mcp/gxp_editor/handoff_import.py:57`、`write/mcp/gxp_editor/state.py:325`；跨仓库测试复用同一份去业务化的交接样例。

## 第二批：减少往返，把可读性写进现有候选复核

3. **Look 一次取齐，Write 只补缺口。** 在现有 `inspect_action` 增加有界批量精读：单次载入指定设计副本，读取最多 10 个精确节点及各自所需参数路径；限制总字节数，逐项标明完整、截断、缺失等状态，带上设计 ID 和内容指纹。发布与草稿分开；续读遇到版本漂移重新锚定。在同一分组需要判断嵌套归属时，合并分支取证，继续使用 `inspect_control_flow` 验证。Write 入口复用交接和已有的 `inspect_edit_context` 摘要、`parameter_paths`；大值按需读，续改走现有 `revise_canvas_plan`。技能主流程明确为「定位 → 批读 → 只补缺失项」，不要默认逐字段回查或自动翻完分页。入口：`look/mcp/server.py:292`、`look/mcp/gxp_core/service.py:333`、`write/mcp/server.py:155`。测试覆盖同副本只加载一次、版本漂移、分组混合、截断与单目标兼容。

4. **Write 在原有候选复核中检查画布差异。** 现有 `readability.md` 已要求原生条件和注释，但只能靠生成者自查。同步修改技能和开发文档，把以下检查放到 `plan_canvas_patch` 的现有业务复核，绑定候选指纹。问题给出分组、节点、参数路径、原因和修法，沿用现有审批入口。复核只看本次新增或实际改动的逻辑，未碰的历史问题不拦保存。

   - 用原生条件、查询、调用和赋值表示可等价的步骤。对可确定的反模式设置阻断：已知可写业务或改界面的操作藏在变量初值里；把一整条已可用原生条件表达的复杂判断搬进紧邻 IF 的一次性布尔变量，判断仍不在画布上。纯计算若短小、职责单一或确需复用，可以保留。检测依据用节点契约和解析后的表达式；长度、层数、运算符数量只提示，不能单凭阈值判失败。原生无法安全等价时保留必要表达式，说明差异和验证依据。
   - 用户要求备注时，在验收要求中绑定具体业务块。对明确要求注释的块，以及新增或实质改写的关键业务块，在入口放原生 **`CustomExt`**，通过普通插入操作写 `input_params.content`。内容是单行、非空的中文业务说明，解释触发原因、适用范围或跳过条件；不每步重复说明，不用标题、变量中文别名或一个远离对应分支的注释充数。复核目标块内的节点类型、位置与文本；注释不替代表达式拆解。验收要求随原计划保留，`revise_canvas_plan` 不能靠删掉要求通过。原生契约见 `look/vendor/cpm-cli/skills/cpm-platform/references/elements/Debug/CustomExt.md`。
   - 先用截图和合成反例跑离线检查。确认没有误拦短纯表达式、原生选择器、字段映射、未改历史节点，再把高置信问题接到现有阻断状态。使用现有复核与生成结果，不增加工具往返、编译轮次或人工审批轮次。入口：`write/skills/gxp-lowcode-edit/references/readability.md:51`、`write/mcp/gxp_editor/service.py:1180`、`write/mcp/gxp_editor/logic_review.py:496`。沿用仓库的原生生成、JS/C# 编译、人工审批、签名和保存核验。

## 第三批：用截图验收，再推广

第一条回归用例是截图里的 `shouldDefaultReviewReviser`。历史草稿在「组件初始化」和「默认复审修订责任人」各有一处相同判断；回归应覆盖两个入口，以现在的草稿确认处理位置。预期维护者从画布就能读到这条链：

1. 放原生注释：**「新版复审在新增页或待办发起节点补默认修订人；修订模式下，修订人为空且能取到本次复审发起人时带入，已有值保留。」**
2. 暴露流程标识和版本 `≥16`；再展示 `新增页 OR（发起节点 AND 待办来源 AND 流程处理中）`；再检查修订模式。新增页仍跳过工作流信息查询，后面的条件不提前执行。
3. 明确检查修订人组件存在，按原规则处理空数组与空字符串表示（包括 `[]`、`null` 的字符串）；`UserId` 组件存在且 ID 去空白后非空时，带入原来的复审发起人。保留原赋值的 `await`、成员结构与调用次数；若原生赋值元件不能等价支持该异步调用，把必要表达式留在同一分支并加注说明。变量只保留有用途的局部纯计算；若布尔值只为紧邻 IF 服务，把可见条件留在 IF。使用原生 `condition.Filters` 前通过生成结果确认短路与求值顺序；若原生组合无法证明等价，改用分层条件保留顺序。合并两个入口前，先确认现有调用关系和触发次数。

用同一个 fixture 执行新旧生成结果，对照写入值、写入次数、调用顺序和未命中路径。覆盖版本 15/16、不同或不可解析的流程标识、新增页跳过工作流查询、待办三个条件分别不满足、非修订、组件缺失、空数组和历史空值、修订人已有值、用户 ID 空或非空。现有场景桩不完整支持 `queryData`、工作流信息和缺失组件；首例补受控行为桩或用隔离的生成 JS 测试，未覆盖的分支不算验证通过。画布实际打开检查：注释出现在对应规则前，长判断没有藏回变量，维护者能顺着命中条件找到赋值。

用冻结的同一份样例回放「只读排查 → 交接 → 首个候选」，分段记录调用数、响应体积、首候选时间、缓存刷新和编译耗时。原对话前两轮 `inspect_action` 分别 62 和 51 次；**验收目标**是同样范围的动作取证调用数与回传体积至少各降一半，交接校验通过时不重扫已验证节点，精确查表不会等待全库刷新。端到端耗时单独报告，不把模型、网络等候算成数据库或编译耗时，也不先承诺分钟数。

质量规则通过后，再按当前草稿重新盘点存量。优先整理截图同类且可证明等价的判断、变量里的隐藏写入，再处理大分组；每批锁定明确业务范围，保持已有值、短路、锁和事务、写入顺序、异步回填、异常及返回。按两个仓库各自安装流程部署并新开会话验收；业务整理走正常草稿审批，发布单独处理。
