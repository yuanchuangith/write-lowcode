# 生成速度与准确性排查（2026-10-20）

优先处理两类问题：减少已证实的重复计算；让“需求通过”确实有对应目标的验证证据。编译成功、场景通过、业务需求通过应分别记录。

## 实测范围

使用本机只读历史备份：16 个分组、816 个节点，JavaScript 446 行、C# 1,183 行，实际修改 2 个元件、4 个字段。离线读取文件和本地状态，未连接业务数据库、未执行候选业务代码、未改变历史审批记录。

原生链测量使用同参数 `replace_params`，保留编译器来源检查、事件校验及独立二次生成。它衡量此画布规模下的基础成本，不能代表所有操作类型。下表的原生编译数据为前轮历史基线；本轮合并复核进程后的结果另列于下方。

| 环节 | 本机耗时 | 说明 |
| --- | ---: | --- |
| 注册表首次加载 | 1,199 ms | 包含 Node、来源校验、Git 证据 |
| `compile_patch` | 1,671 ms | 1 次 Node，2 次 manifest 校验 |
| `verify_compiled_result` | 2,469 ms | 2 次 Node，3 次 manifest 校验；事件检查及独立再生成 |

代码对齐优化减少此样本约 80% 的 C# 对比计算时间，不等于整个生成流程提速 80%。来源、编译、生成一致性校验均继续执行。未测量模型推理、网络、真实 SQL、C# 构建或端到端审批时间；目前不能给出整体速度提升或生成准确率百分比。

原始本机测量保存在忽略跟踪的 `output/compiler-offline-profile.json`、`output/generation-offline-profile.json`、`output/code-alignment-comparison.json`。可复用的无数据库基准入口为 `scripts/profile_generation.py`，用法见 `scripts/README.md`。

本轮显示模型复用的结果在 `output/review-display-context-profile.json`：同份报告只生成一次元件差异、控制流影响及两侧位置索引，供证据和数据流视图复用。此样本的模型组合耗时减少约 61%，不代表 Qt 绘制、编译或整个生成流程提速 61%。每次换报告重新生成上下文，不跨报告长期缓存。

## 合并复核进程后的原生实测

本轮仍使用上述 16 组、816 节点的本地历史审批样本。通过 `scripts/profile_generation.py` 的 `--artifact`、`--frontend`、`--repeats 1` 模式，只读取得画布并在内存中应用一次同参数 `replace_params`。各原生阶段仅运行一次，Node 调用上限为 25 秒；没有连接业务数据库、运行候选业务代码或改变历史审批。结果保存于 `output/generation-verification-batch-profile.json`。

| 阶段 | 前轮历史基线 | 本轮单次测量 | 调用次数变化 |
| --- | ---: | ---: | --- |
| `compile_patch` | 1,670.550 ms | 1,994.588 ms | 均为 1 次 Node、2 次 manifest |
| `verify_compiled_result` | 2,468.749 ms | 1,754.182 ms | 2 → 1 次 Node；3 → 2 次 manifest |
| 编译与复核合计，不含首次加载 | 4,139.299 ms | 3,748.770 ms | 3 → 2 次 Node；5 → 4 次 manifest |
| 注册表首次加载 | 1,199.151 ms | 1,778.863 ms | 均包含 1 次 Node、1 次 manifest、5 次 Git |

新命令 `verify_candidate` 在一个独立的新 Node 进程中同时复核事件和执行第二次真实原生生成。Python 仍比较完整 JavaScript、C#、关系数据、画布 validation 和编译器 binding；本轮样本的 `valid`、`code_generation_complete`、`generated_code_consistency_verified` 全部为真。复核进程没有直接复用第一次生成的源码作为自己的结果。

这组数据证实每次编译与复核少启动一个 Node、少扫描一次 manifest。两轮不属于同一批次的受控 A/B，且本轮首次加载与 `compile_patch` 耗时更高；合计的约 9.4% 下降仅是这两个单次观测之差，不能据此承诺稳定提速。当前未测端到端耗时、模型推理或 C# 构建，不能由此推断总体准确率。

## 本轮修正

- 需求与场景证据：原来只凭 `requirement_ids` 和 JS 场景状态即可将 C# 查询需求标为通过。需求判定现在核对目标与执行证据；C# 业务未执行、目标未知、缺少关联执行证据时保留待验证。当前执行器没有节点/配置字段覆盖证据，带 `node_key` 或 `field_path` 的需求保持待验证；事件触发记录也不凭静态绑定推断成具体回调的执行证据。JS 整组需求可由对应分组调用与关联场景断言验证，不能据此证明某个分支或节点被执行。
- 需求范围：将 `targets` 纳入需求版本变化判断，避免通过放宽目标范围而省略新的用户依据。
- 来源绑定：注册表缓存命中时重新核对全部 adapter 文件的 hash，避免旧绑定证据对应新 adapter 行为。
- 显示性能：临时变量识别使用预编译表达式、按提取出的动作名查集合，减少逐动作重复匹配；没有候选临时变量时提前返回。字符串、注释、成员名和业务差异继续保守处理，可复制源码保持原样。
- 参数合同：明确 `replace_params` 完整替换输入和输出字典，遗漏字段不会自动保留。修改一个筛选也必须保留其他筛选、AND/OR 结构及输出映射。

## 本轮继续优化

- 局部参数修改：新增 `set_parameter`，必填目标元件类型、已有 JSON pointer 路径、完整原值和新值。程序复制其余输入与输出，交真实原生生成；原值过期、目标歧义或类型不符时拒绝。原生生成如连带改变其他参数也拒绝，不会静默接受规范化。顺序批次逐步核对原值，原有整草稿并发检查保留。
- 适用边界：只穿过已有字典路径，不支持数组索引或新增字典键；筛选数组须提交完整旧数组及完整新数组，保留原行与 AND/OR 结构。已知原生 ParamInput 的表达式要整条记录更新，保持 `value` / `code` 同步。它减少重发无关参数的必要，但本轮未测量模型输入量或首次生成通过率。
- 配置断言：`review_spec.canvas_assertions` 支持严格 JSON `equals`、数组完整成员 `contains` 和基线 `unchanged`，关联固定需求与真实元件身份。错误筛选、AND/OR 结构、输出或目标会形成失败证据并阻断审批；准备审批时重新核对真实画布。修改或删除既有断言需要新 revision 和新用户依据，不能删失败检查求通过。
- 证据分离：新增“配置核对”页签，展示预期、修改前后、结果，并按真实画布行号定位元件。仅部分配置断言通过不能将整个需求配置范围标为已核对；配置状态与场景/执行状态分别记录。静态通过不表示真实查询、浏览器或后端业务已运行。
- 显示复用：本份报告的差异、位置和控制流分析供多个模型复用，保持原返回结果；换报告时清空旧证据及定位状态。

## 后续优先级

报告驱动的接口优化也已完成：`inspect_edit_context` 直接读取会话备份的目标上下文；规划与审批 MCP 默认返回摘要，完整证据按需分页；空 C# 不再自动探测 SDK/DLL；同一工具请求内复用组件实例。新 `set_array_item` 支持按唯一稳定 id/key 修改完整行，不允许裸索引，缺稳定键时继续整数组更新。

200 节点、400 条差异的固定合成报告，紧凑 JSON 编码的摘要响应为 **546 字节**，完整报告响应为 **183,782 字节**，报告 hash 不变。仅衡量 `review_response` 报告部分，不能当作所有工具响应的固定压缩比例。记录在 `output/review-response-profile.json`；完整参数与报告未从审批产物中删除。

本轮报告驱动优化共 282 项 Python 联合回归通过，包含真实原生桥的参数生成和产物篡改拒绝，另有 31 项 Node 单测通过。目标读取与报告分页在返回前复核会话归属版本；旧无范围策略报告可读，但新审批和写入执行必须重新规划。无变化操作不启动原生生成，且明确说明已有计划仍保留，不把它自动转入审批。

| 优先级 | 改进 | 预期作用 | 验证方法 |
| --- | --- | --- | --- |
| P1 | 建立固定脱敏需求集，量化新增参数操作及配置断言的收益 | 测量首次计划通过率、未请求配置保留率和模型输入量 | 冻结预期；同时覆盖正常需求与故意漏条件、误目标、误输出的候选 |
| P2 | 在已合并复核进程的基础上，研究单次受控操作内复用来源快照 | 当前编译及复核仍有 4 次 manifest 全量校验；避免重复扫描仍有空间 | 分别记录启动、扫描、原生编译时间；期间替换 source/bridge/adapter 必须拒绝；仍逐项比较 JS、C#、关系数据，不跨会话缓存 |
| P2 | 用已实现的会话目标上下文工具衡量定位收益 | 减少无关上下文；先定位、再读取至多 10 个节点完整参数 | 记录输入量、工具调用数、误定位率及遗漏引用率；不能裁掉相关分支、输出和引用 |

进程复用与来源缓存需要专门设计边界：独立二次生成继续保留；准备审批时重新核验当前草稿、编译器绑定和候选产物；执行阶段继续验证签名及事务产物。不能将规划阶段成功当作写前成功。

## 如何衡量准确率

目前只有一个真实复杂历史样本和缺陷回归，无法估算总体生成准确率。建议建立固定的脱敏需求集，覆盖 JS/C#、增删改移、分支、事件、参数/输出保留、无效引用和同名元件定位，并冻结预期，避免失败后修改答案。

每个样本同时记录首次计划通过率、误改节点或字段率、未请求配置保留率、业务需求通过/失败/待验证比例，以及分阶段与端到端 p50/p95 耗时。场景缺断言、不支持 API、未执行 C# 或未覆盖目标，应记录为待验证；不得计入正确样本。
