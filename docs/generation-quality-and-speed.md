# 生成速度与准确性排查（2026-10-20）

优先处理两类问题：减少已证实的重复计算；让“需求通过”确实有对应目标的验证证据。编译成功、场景通过、业务需求通过应分别记录。

## 实测范围

使用本机只读历史备份：16 个分组、816 个节点，JavaScript 446 行、C# 1,183 行，实际修改 2 个元件、4 个字段。离线读取文件和本地状态，未连接业务数据库、未执行候选业务代码、未改变历史审批记录。

原生链测量使用同参数 `replace_params`，保留编译器来源检查、事件校验及独立二次生成。它衡量此画布规模下的基础成本，不能代表所有操作类型。

代码对齐优化减少此样本约 80% 的 C# 对比计算时间，不等于整个生成流程提速 80%。来源、编译、生成一致性校验均继续执行。未测量模型推理、网络、真实 SQL、C# 构建或端到端审批时间；目前不能给出整体速度提升或生成准确率百分比。

原始本机测量保存在忽略跟踪的 `output/compiler-offline-profile.json`、`output/generation-offline-profile.json`、`output/code-alignment-comparison.json`。可复用的无数据库基准入口为 `scripts/profile_generation.py`，用法见 `scripts/README.md`。

本轮显示模型复用的结果在 `output/review-display-context-profile.json`：同份报告只生成一次元件差异、控制流影响及两侧位置索引，供证据和数据流视图复用。此样本的模型组合耗时减少约 61%，不代表 Qt 绘制、编译或整个生成流程提速 61%。每次换报告重新生成上下文，不跨报告长期缓存。

## 本轮修正

- 需求与场景证据：原来只凭 `requirement_ids` 和 JS 场景状态即可将 C# 查询需求标为通过。需求判定现在核对目标与执行证据；C# 业务未执行、目标未知、缺少关联执行证据时保留待验证。当前执行器没有节点/配置字段覆盖证据，带 `node_key` 或 `field_path` 的需求保持待验证；事件触发记录也不凭静态绑定推断成具体回调的执行证据。JS 整组需求可由对应分组调用与关联场景断言验证，不能据此证明某个分支或节点被执行。
- 需求范围：将 `targets` 纳入需求版本变化判断，避免通过放宽目标范围而省略新的用户依据。
- 来源绑定：注册表缓存命中时重新核对全部 adapter 文件的 hash，避免旧绑定证据对应新 adapter 行为。
- 显示性能：临时变量识别使用预编译表达式、按提取出的动作名查集合，减少逐动作重复匹配；没有候选临时变量时提前返回。字符串、注释、成员名和业务差异继续保守处理，可复制源码保持原样。
- 参数合同：明确 `replace_params` 完整替换输入和输出字典，遗漏字段不会自动保留。修改一个筛选也必须保留其他筛选、AND/OR 结构及输出映射。

## 本轮继续优化

- 局部参数修改：新增 `set_parameter`，必填目标元件类型、已有 JSON pointer 路径、完整原值和新值。程序复制其余输入与输出，交真实原生生成；原值过期、目标歧义或类型不符时拒绝。原生生成如连带改变其他参数也拒绝，不会静默接受规范化。顺序批次逐步核对原值，原有整草稿并发检查保留。
- 适用边界：只穿过已有字典路径，不支持数组索引或新增字典键；筛选数组须提交完整旧数组及完整新数组，保留原行与 AND/OR 结构。已知原生 ParamInput 的表达式要整条记录更新，保持 `value` / `code` 同步。它减少重发无关参数的必要，但本轮未测量模型输入量或首次生成通过率。
- 配置断言：`review_spec.canvas_assertions` 支持严格 JSON `equals`、数组完整成员 `contains` 和基线 `unchanged`，关联固定需求与真实元件身份。错误筛选、AND/OR 结构、输出或目标会形成失败证据并阻断审批；准备审批时重新核对真实画布。修改或删除既有断言需要新 revision 和新用户依据，不能删失败检查求通过。
- 证据分离：新增“配置核对”页签，展示预期、修改前后、结果，并按真实画布行号定位元件。仅部分配置断言通过不能将整个需求配置范围标为已核对；配置状态与场景/执行状态分别记录。静态通过不表示真实查询、浏览器或后端业务已运行。
- 显示复用：本份报告的差异、位置和控制流分析供多个模型复用，保持原返回结果；换报告时清空旧证据及定位状态。

| P2 | 按目标节点提供所需元件合同、相邻控制流与引用证据 | 减少无关上下文；沿用当前先定位、再读取至多 10 个节点完整参数的流程 | 记录输入量、工具调用数、误定位率及遗漏引用率；不能裁掉相关分支、输出和引用 |

## 如何衡量准确率

目前只有一个真实复杂历史样本和缺陷回归，无法估算总体生成准确率。建议建立固定的脱敏需求集，覆盖 JS/C#、增删改移、分支、事件、参数/输出保留、无效引用和同名元件定位，并冻结预期，避免失败后修改答案。

每个样本同时记录首次计划通过率、误改节点或字段率、未请求配置保留率、业务需求通过/失败/待验证比例，以及分阶段与端到端 p50/p95 耗时。场景缺断言、不支持 API、未执行 C# 或未覆盖目标，应记录为待验证；不得计入正确样本。
