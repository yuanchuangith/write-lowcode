# Look / Write 技能速度与准确性优化报告

日期：2026-10-26。范围：技能指引、MCP 服务实现、离线验证和现有测量材料。本轮先交付报告及测量附件，没有继续修改运行逻辑、安装插件、连接业务数据库、保存或发布草稿，也没有提交 Git。

## 1. 结论与建议顺序

**还有优化空间，优先减少重复工作并补强证据校验。当前证据不足以承诺整体提速比例或真实业务准确率。**

用户补充了“大配置回传模型导致慢”的实际观察，**模型输入减量应提升为 P1，和完整调用链测量一起优先处理**。现有编译桥计时不包含这部分。具体来源、已有可用参数和后续方案见第 8 节。

1. **准确性先补两个边界：**Write 场景报告的断言完整性校验；Look 索引证据与即时源码读取的一致性。前者已在内部函数内存样例中复现，后者是代码确认的竞态窗口，尚未复现现场误判。
2. **速度先做可核对的小改：**Look 控制流停止读取未用到的生成 C#，后端调用链使用请求内邻接表；Write 核对开始编辑和准备写入阶段的重复来源扫描。全部保留原有身份、来源和写入边界校验。
3. **建立固定业务错改语料和服务层基准，再处理较大改动：**大画布分页、图谱查询工作量和验证并行化。以错误检出、未验证比例和完整请求耗时共同验收。

本次新测的 6 节点小画布中，`full`、`incremental`、`auto` 中位耗时分别为 **4257.687 / 4129.485 / 4275.409 ms**，范围重叠。`auto` 三次均选择增量，但没有表现出稳定的耗时优势。**不建议据此切换默认生成模式或放宽自动模式阈值。**

## 3. 本次速度测量

### 3.1 Write：三种生成模式

方法：6 个 JS 分组，每组 1 个 `SetVariable`，修改其中 1 个节点的数值；全部模式提供同一完整基线画布和已保存产物。每模式预热一次，再各测三次，轮换顺序以平衡位置影响。每次请求新建桥接对象，复用进程内规则缓存；生成后启动独立新 Node 复验。不包含非空 C# 编译。

## 4. 准确性改进

### A1 · P1：验证场景报告的完整断言，而不只接受 passed

**证据：本次内部函数内存复现。**人工构造当前 runner 版本的报告，固定期望 `result="after"`，报告实际值为 `"wrong"`，状态却为 `passed`，trace 包含 `group.main`，完全省略 `assertions`；画布、范围和摘要满足其他校验。`build_business_review` 和 `validate_business_review` 接受它，得到通过且未知项为 0。

位置：[Write logic_review.py:412](../mcp/gxp_editor/logic_review.py:412)。仅当 assertions 不是 None 时检查列表；字段缺失或为 null 会跳过检查，空列表则会被拒绝。校验也未核对断言是否完整对应固定期望。

**实际影响边界：**这是内部证据校验缺口。真实 runner 会生成断言并按断言计算状态，服务直接调用该 runner；未发现用户提交任意 scenario_report 的业务入口，也未证明错误修改可绕过审批。真实路径见 [logic_scenario_runner.cjs:193](../mcp/gxp_editor/logic_scenario_runner.cjs:193)、[service.py:910](../mcp/gxp_editor/service.py:910)。

**建议：**当前版本声称 passed 的结果必须有完整断言；由固定 expect 推导允许的断言集合，核对名称、数量、存在性、期望值、观察值和 passed 状态。对数据型期望重新比对，无需再执行 JS。超时、不支持、执行中抛错等结果可以没有完整断言，保留其未验证或失败状态。旧报告缺证据时只读或标为未验证。

**验收：**缺失、空列表、少一项、错名称、错期望、实际不符但标真、重复断言均拒绝；真实完整报告继续接受。保留 passed / failed / unverified 三态。成本低至中。

### A2 · P1：固定索引证据与即时源码读取的版本

**证据：当前代码确认，竞态尚未在现场复现。**Look 查询开始确保索引新鲜，前后核对 generation；但部分实现又直接读当前源码，结束时没有核对这些文件仍属于索引版本。文件在状态检查后改变、索引 generation 未变时，可能混用两份版本。

位置：[Look source_analysis.py:58](../../look/mcp/gxp_core/source_analysis.py:58)、[即时读取:130](../../look/mcp/gxp_core/source_analysis.py:130)、[异常流读取:449](../../look/mcp/gxp_core/source_analysis.py:449)。

**建议：**优先将所需结构信息一并写入索引；仍需即时读取时，只核对本次读取文件，将内容指纹与构建该索引 generation 时保存的文件指纹比对。只检查读取期间是否变化还不够，文件可能已在状态检查后、即时读取前改变。发生不一致就重试受限次数或降级 unresolved，避免增加全仓库扫描。

**验收：**临时仓库在状态检查后修改目标源码，输出必须来自固定版本或明确未解决；覆盖同长度改写、单层变化和连续变化，保留既有按层失效与 generation 重试保护。成本中。

### A3 · P2：让图谱截断提示指向完整案例快照

**证据：当前文本与新契约不一致。**写后响应截断提示仍建议 `get_business_graph` 获取 complete supports；邻域有支持数量与响应限制，新契约明确不能据此拼完整案例。

位置：[Look business_graph_store.py:413](../../look/mcp/gxp_core/business_graph_store.py:413)、[案例替换契约:22](../../look/skills/gxp-lowcode-debug/references/business-logic-graph.md:22)。

**建议：**返回精确 `case_key + scope_id + environment` 的 `search_business_logic_graph` 续查方式，要求检查 available / found / complete / replacement_safe；超限不能当作不存在。沿用快照令牌，并保留同一 case_key 是完整支持集替换的语义。

**验收：**强制触发写后截断，能直接恢复完整案例或明确超限；不需要遍历邻域。成本低。

### A4 · P1：补“错改能否被发现”的独立业务语料

现有 JS 场景能验证声明的输入与期望，但 C#、节点执行、字段业务效果不一定能由它证明。组被调用也不保证关键分支执行或字段写对。这些应继续保守标为未验证，不能用通过率掩盖证明范围。

建议首批固定 8 类脱敏模板：新增/编辑模式、AND/OR、空值/空数组、字段误绑、分支外写入、回调 payload、连续事件 metadata 残留、输出结构。每类 1 个正确版本、至少 2 个错改版本，共至少 24 个固定版本。期望由原始需求独立编写，不能根据候选运行结果倒推。拆分小套件，遵守每批 20 场景与总时限。

另加 12 个归因样例，覆盖组被调用但分支未执行、错误字段写入、事件绑定后续覆盖、C# 目标只配 JS 场景。先明确覆盖能力，再决定是否增加由原生编译结果定位的节点/回调执行标记。位置：[需求证据逻辑:227](../mcp/gxp_editor/logic_review.py:227)、[现有错改测试:258](../tests/test_logic_scenarios.py:258)。

验收首先要求支持范围内错改误绿为 0，不支持样例仍为未验证；正确版本的误阻单独计数。它是固定语料的检出结果，不命名为线上准确率。成本中。

| 技能路由 | 12 组同义表达：只读排查/草稿修改、动作歧义、运行副本与草稿、已保存后续查、等待审批、图谱精确案例读取 | 首次正确工具路由、错动作/错副本、无必要调用数、工具往返数；不能只查技能文字是否包含关键词 |
| 业务错改 | 8 模板 × 至少 3 版本，原始需求预先固定期望 | 正确版误阻率、错误版检出率、误绿数、未验证率及原因；分母分开 |
| 证据归因 | 12 个组/分支/字段/节点/C# 覆盖样例 | 错目标归因误绿数；场景、事件、配置、执行证据分别统计 |
| 模式与变旧证据 | 6 种子 × full/incremental/auto，涵盖旧引用、复制/移动引用、不可达变可达、声明/事件输入、调用依赖变化、计划后草稿/relations/来源/期望变化 | 新问题漏检 0、允许保留的已证实基线问题误阻 0、陈旧证据全部拒绝；跨模式业务结论分歧单列，源码文本差异按保留策略解释 |
| 服务层性能 | 小/千节点画布，发现首/末页、上下文、begin、plan、prepare；混合 JS/C# 另测 | 请求 wall time、生成/验证/来源/DB 分段、Node/dotnet/SQL 次数、响应字节、峰值内存、工具往返数 |

“允许保留的基线问题”限定为未新增、未改变声明或可达性、且不违反用户固定验收规则的已证实旧问题，不能将它理解为所有历史问题都应放行。

“误绿”指错误样例被声明为 passed；unverified 进入人工审阅不计为误绿。错误检出分别统计明确失败、校验拒绝和未验证，不能将三者合并成同一种成功。

每个性能场景至少 5 次做探索，报告中位值和范围；需要评估尾延迟时，收集足够的同类请求（建议至少 30 次，仍注明分位数不稳定性），不以 3 次样本或 5 个轮均值宣称可靠 p95。冷/热状态明确区分，基线与候选同机轮换；不得拿不同日期数据直接计算优化收益。

离线服务层可以模拟 DB 与审批启动，结果必须标为模拟。真实端到端耗时在后续已授权任务中按 trace 观察，模型思考、工具传输和人工等待分别记录，不能合并后归因给编译优化。指标只记录时间、数量、状态和指纹，不把业务参数或凭据带入性能日志。

### 必须保留的正确性边界

- 精确动作/副本/节点定位；有歧义时继续补证，不静默选一个。
- Node 独立再生成与产物比对、非空完整 C# 编译、来源绑定与变旧检查。
- 草稿、relations、固定期望、会话所有权和审批绑定；性能缓存不能跨越这些变化。
- 图谱完整案例、完整支持集替换与乐观并发令牌；截断/超限不能当作完整或不存在。
- 失败与未验证分别表达；正样例跑通、测试全绿、响应变短均不能单独代表业务准确率提高。

## 8. 补充：大配置返回模型的减量方案（P1）

### 8.1 处理原则

**完整配置保留在服务端的版本化快照或本地审批产物中，模型默认获取定位摘要，只在当前判断需要时读取具体字段和差异。**这样同时减少传输量、模型输入量以及无关配置掩盖关键证据的机会。

目标流程：`动作/分组摘要 → 节点 Key → 所需参数路径及条件 → 修改差异摘要 → 必要时精读异常项`。不能把分页变成自动读完全部页，否则只是增加往返。只去空格、gzip 压缩能节省部分传输字节；若最终仍向模型展开完整 JSON，模型需要处理的主要内容仍在。

### 8.2 当前已经可以使用的能力

| 工具/路径 | 现有机制 | 建议调用方式 |
| --- | --- | --- |
| Look inspect_action | 默认不含完整参数和生成 C#；默认 20 节点、32 KiB，预算可选 8～64 KiB | 先用精确 group/node、terms/focus_fields 定位；小查询可选 max_nodes=5、max_output_bytes=8192；确有需要再读取目标参数 |
| Look 参数值续读 | value_path 可精确到 /paramsValue 内 JSON Pointer；value_limit 按字符，默认 2048，单片另有序列化字节约束 | 沿返回的 next_offset 读取必要片段，续页固定 design_id；不要自行假定每次返回固定长度 |
| Look 控制流 | 已有 render、include_relations、follow_calls、节点/边数与字节限制 | 当前任务只需树时使用 render="tree_text"，不索要全部表示形式和调用展开 |
| Write 节点发现 | find_edit_nodes 只返回位置和标签，不带参数或源码 | 先找 Key，再对一个目标精读，避免一次带回 10 个目标的完整上下文 |
| Write 编辑上下文 | include_context=false 可省去完整 params、父参数、变量目录和原生契约；操作模板有分页 | 已有足够语义证据时使用紧凑模式，缺条件/声明时再取必要完整上下文；不能把省略字段当作不存在 |
| Write 计划与准备写入 | MCP 外层 plan_canvas_patch、open_plan_review、prepare_write 已默认 response_detail="summary"；read_plan_review 可按 section/item_id 分页 | 保持摘要默认；按问题 ID 精读相关一项，避免主动请求 full 或完整 spec |

位置：[Look inspect_action 参数](../../look/mcp/server.py:285)、[值分页](../../look/mcp/gxp_core/canvas_budget.py:51)、[Write 上下文选项](../mcp/server.py:147)、[Write 计划默认摘要](../mcp/server.py:165)。这些能力已经存在，不能再次算作新增实现。

历史固定报告样例中，review_response 报告部分从完整 183,782 字节变为摘要 546 字节，报告 hash 保持不变。这只说明摘要投影可以大幅减少该样例的报告内容，不是全部工具响应的固定压缩比或端到端提速比例。见 [已有报告投影测量](generation-quality-and-speed.md:66)。

### 8.3 尚需改进的具体路径

| 优先级 | 当前问题与证据 | 建议实现 | 正确性与验收 |
| --- | --- | --- | --- |
| P1 | Write 首次 inspect_edit_context 默认完整上下文，含目标完整参数、父参数、变量目录及原生契约；上限 1 MiB 仍远大于一般定位需求。[edit_context.py:205](../mcp/gxp_editor/edit_context.py:205)、[完整投影:232](../mcp/gxp_editor/edit_context.py:232) | 增加 field_paths / section 投影，先回参数目录、类型、长度及必要条件，再读将修改的值；原生契约按版本只取需要的条目 | 摘要保留省略清单、版本绑定、完整性状态和明确 next_read；必须能补齐影响当前判断的条件/声明，避免少读造成误改 |

| P2 | begin 在 matched handoff 时嵌入完整 edit_context；没有响应摘要选项。[service.py:566](../mcp/gxp_editor/service.py:566) | begin 默认身份、绑定、就绪和目标摘要，完整上下文另读；避免重复 begin 获取同一配置 | 保留证据是否已匹配与是否过时的区别；完整审批/备份内容保持可核对 |
| P2 | Write 报告按记录数分页，limit=1 仍可能返回很大的 before/after 或 observed；超大项目前缺字段级续读。[review_response.py:46](../mcp/gxp_editor/review_response.py:46) | 增加 item_id 内字段/path 读取和字节预算；默认返回变更路径、类型、长度、短预览及详情引用 | 不能靠“每页一条”保证体积；预览明确不完整，精确值可恢复读取，报告 hash 与版本固定 |
| P2 | Look 过滤器 writer 列表和异常追踪没有统一输出预算；异常候选列表存在重复别名，JSON 会重复序列化。[service.py:750](../../look/mcp/gxp_core/service.py:750)、[diagnostics.py:395](../../look/mcp/gxp_core/diagnostics.py:395) | 增加摘要投影、计数、按项续查和预算；实体只输出一次，其他位置用 ID 引用；兼容旧调用 | 所有 writer/候选仍可查到，不能静默丢失；版本固定，歧义与未读状态保留 |

推荐正常定位响应以 **8～16 KiB** 作为探索目标，详情响应设置独立预算与续读入口；这是待验收目标，不是当前所有工具已有的限制，也不等于固定 token 数。原子参数若无法安全拆分，应显式报告并走服务端引用/完整审阅路径，不能截断后拿去更新。

图谱摘要可用于检索定位，但同一案例的完整支持集替换仍要求精确完整快照和令牌。若以后要让大案例替换也不经模型搬运全量配置，应另设计服务端快照绑定的变更集接口；当前不能用摘要覆盖整案。

### 8.4 新增测量与放行依据

对一条完整流程记录：**工具端 wall time、实际 MCP 序列化响应字节、模型输入 token（可用时记录实际 usage，否则标为估算）、首次答复/总耗时、工具往返次数、重复大值返回次数、未验证状态**。字节数与 token 数分开，核对客户端是否重复注入同一 text/structured 内容；当前未确认存在这种重复。

用小参数、大数组、超长表达式、多父节点、重复原生契约、报告大单项各一组，比较旧/新完整流程。验收要求：相关字段与旧值保护不丢失，完整审批证据不变，摘要/续读绑定过期时拒绝；总返回量显著下降，且新增往返没有抵消端到端收益。现有 inspect_action 的小输出仍可能先加载整个设计，返回减量与 DB/后端处理减量应分别测量。

建议将这一项置于第二批较大性能改动之前：先规范现有紧凑调用，再实现 Write 按字段读取、去重 guard 和服务端原值引用。本节仅补充报告，未修改运行逻辑。
