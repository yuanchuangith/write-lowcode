# 指定对话性能复核

本次仅统计用户指定的一个 Codex 对话 JSONL。记录时间为 2026-11-05 08:57 至 14:39（Asia/Shanghai）；不读取其他对话、凭据或业务数据库，统计报告不包含对话正文、业务配置、命令参数或会话标识。

## 优化方向

首先减少持续带入上下文的内容：正常定位使用摘要；只读取实际要改的 `parameter_paths`；长旧值使用既有签名守卫，完整字段按需分页读取。30 次全量上下文读取与 18 次大规划请求均有实测体量依据。保留已有计划和会话，避免没有新证据的重复定位；相同参数的状态读取可能用于核对新保存或发布，不能仅凭参数相同删除。

同一草稿已确认的小修改尽量一起规划，避免每补 1 至 5 个操作就再次全量生成及编译。保留原生生成、完整候选检查、审批绑定和保存核对；是否切换增量模式须使用项目已支持的模式和来源验证。

长对话的输入已接近记录窗口，后续应缩小任务工作集，按目标保留简短状态与可重读证据。降低推理档位或调整上下文策略属于客户端偏好，应另行明确；本复核不修改全局配置。缓存命中比例高也不能据此断言长上下文没有延迟成本。

## 已落地的兼容优化

本轮保留模型和推理档位，不修改全局 Codex 配置。插件版本更新为 `0.1.63+codex.local-20261106-context-latency`，源码交付不自动更新正在运行的客户端。

- `inspect_edit_context` 的摘要可内联明确完整的小参数（单值 1 KiB、整次 4 KiB），并按需分页返回完整可见变量引用（整次 2 KiB）。无需为了变量或一个小记录读取全部父参数及元件契约，完整模式仍兼容保留。
- `guard_ref` 新版只传版本和 HMAC；完整会话、来源、目标、选择器及旧值指纹在服务端重建校验，旧版仍可校验。同一 8 模板离线样本从 9,729 降至 1,969 字节，展开后的完整操作完全一致，不改变原生生成、业务复核、并发或人工审批。
- 操作输入按实际 `operation` 和旧值模式选择唯一验证分支，保留原公开 `anyOf` 结构及严格类型规则。同一缺字段样本从 81 条、18,065 字节错误降至 1 条、510 字节，避免无关分支错误反复进入上下文。
- 技能明确按参数路径读取，只输出 MCP 结果的一份完整表示，复用未变化的会话验收要求，并合并已确认的同草稿修改；不把分步追加当作每个节点的固定步骤。

合成场景中，指定参数和变量页的摘要为 4,582 字节，原全量响应为 115,371 字节。两者的读取范围不同，未选中的证据仍按需可读；这是体量测试，不是对原对话端到端耗时的重放或加速比例。另一较小 fixture 五组交替读取均为全量 35,201、摘要 4,641 字节，所需参数完整。暂不改仅约毫秒级的 SQLite 初始化或亚秒级的 Node 探测，避免把小项包装成数分钟延迟的根因。

## 第二轮：减少重复规划与大请求重写

继续查看同一记录后，没有发现足够依据把不同页面的定位读取当作冗余。更明确的浪费是：4 次后续请求的操作与此前成功计划完全相同，共重复传入 204,034 字节操作；需求说明仅修改少数记录，却重传完整场景。该对话唯一没有建立计划的规划请求因验收依据校验失败，不是编译失败，因此本轮没有新增复杂的失败请求暂存。

新增 `revise_canvas_plan`：按当前计划 ID 保留完整操作，只传带原操作哈希的整条替换；`review_spec_update` 按 ID 更新完整需求或断言，不删除记录，不隐式改变场景和范围。场景修改、删除或范围调整仍走完整 `review_spec` 及原有用户依据门禁。

对原日志中的 4 个相同操作请求进行本地纯数据重建，完整有效验收规范均与原请求精确相同；未执行其中的任何业务动作：

| 原请求字节 | 计划引用及验收更新字节 | 验收规范精确一致 |
| --- | --- | --- |
| 128,050 | 16,343 | 是 |
| 128,355 | 16,648 | 是 |
| 135,997 | 1,313 | 是 |
| 10,870 | 1,316 | 是 |

相同操作的重复规划原记录仍执行 C# 校验约 5.6–5.8 秒、原生画布生成约 1.5–2.0 秒；其中一次新业务复核仅约 0.23 秒。新代码把完整候选及生成/编译证据摘要绑定到计划哈希，仅当前最新计划、同一基线、完全相同操作与生成模式、源码及引用内容核对一致时复用候选。旧计划缺证据承诺则正常生成，篡改或归属漂移直接拒绝。当前场景和业务复核始终重新执行，创建新计划并替代旧计划，不继承任何审批。

此优化只帮助已有候选的续改；首次规划、操作内容变化或引用不能复用时仍完整生成和编译。保存审批及执行的最终检查保持。原生集成测试覆盖 103 操作、21 个场景各 11 步，在禁止再次调用画布生成器的条件下修订成功，再走单次审批；没有实际业务 SQL。新增 `candidate_reused` 与 `review_reexecuted` 分开报告，避免把复用描述为重新编译。

本轮版本为 `0.1.64+codex.local-20261106-plan-revisions`。仍不改模型和全局推理设置；源码更新不自动安装到已运行客户端。这里的请求体量对照和旧阶段耗时不是整段对话端到端加速测量。

审批准备的旧记录还有未被分阶段覆盖的时间，新增 `approval.preflight` 和 `approval.launch` 计时，后续可区分最终适用性核对与窗口启动；计时不包含业务正文，也不进入任何审批签名。没有根据缺失计时取消数据库或身份检查。

## 复核脚本与限制

运行 `python scripts/profile_codex_thread.py <精确JSONL文件> --output output/thread-latency-20261106.json`。脚本不搜索其他对话，只输出 metadata 统计；按 `response_id` 和已完成 MCP 调用 ID 去重，并使用区间并集处理嵌套及并行工具。结果 JSON 保存在已忽略的 `output/` 下。

大小是 JSON 序列化估计，可能同时包含 MCP text 与 structuredContent 两份内容，部分记录已被运行器裁剪，不能作为真实网络字节。缺少服务器计时的调用只能使用调用 duration；没有显式压缩事件也不能证明服务端内部完全没有处理上下文。测试 `tests.test_codex_thread_profile` 覆盖去重、active/idle、并行区间、未知间隔、体量计数和正文隐私保护。

日志位置依据为 [OpenAI Docs：反馈与日志](https://developers.openai.com/codex/app/troubleshooting#feedback-and-logs)；以上耗时与字节数字来自用户指定的本地记录及离线测试，不是官方性能保证。
