## 2. hash 方案：复用现有绑定，补比较结果和差异说明

采纳“每份关键数据有 hash，恢复时比对”的思路。hash 用来确认当前快照是否匹配，进程存活、是否批准、是否执行及是否由某事务提交，需要其他证据共同判断。

| 对象 | 当前已有机制 | 本次增量 |
| --- | --- | --- |
| 草稿整体 | `design_content_hash` 包含身份、data、JS、C# 和修改时间 | 保留原算法；新增排除修改时间的诊断用 `payload_sha256`，区分正文变化和仅版本时间变化 |
| 草稿各字段 | 候选已有部分字段摘要 | 对基线和当前的 data/JS/C# 给出必要的字段摘要与变化布尔值，解释变化范围 |
| 关系集合 | `relation_snapshot_hash` 包含行身份、归属、正文、删除及审计字段，稳定排序 | 复用完整集合摘要；需要定位时才按关系 ID 给出差异，不扫描全库 |
| SQL、参数、预期行数、前后指纹 | `statement_hash` | 直接复用，不另建参数级签名体系 |
| 事务、计划、编译和业务验证证据 | 计划绑定、`transaction_binding_hash`、compiler binding | 重开前重新验证适用性，不仅验证本地文件格式 |
| 人工审批 | HMAC、事务/语句绑定、有效期 | 保留；hash 相同不会新增审批，过期审批仍须重新取得 |
| 运行资源 | 部分 adapter 文件已参与编译绑定 | 增加完整运行文件字节 manifest，与实例版本绑定 |
| 队列 | 成员、顺序、owner revision、当前事务 | 增加短时控制协议、generation/revision 与规范化成员摘要 |
| 心跳、审批进度和执行状态 | 可变状态 | 使用状态机、单调事件序号及执行 claim；不要求整个 JSON 文件 hash 恒定 |

新增诊断摘要采用版本化口径，使用现有 UTF-8/SHA256 与确定性 JSON 实现。代码正文不去空格、不转大小写、不忽略换行；列表顺序保留，关系排序复用现有规则。需要区分缺字段与空值的诊断摘要显式记录字段存在性。相同摘要只有在 schema、对象身份和作用域一致时才比较。

现有 `content_hash`、关系 hash、SQL CAS、审批 HMAC 算法及旧工件签名内容不变。诊断字段、心跳、耗时和恢复建议不加入审批绑定，也不修改旧工件。新事务若增加账号身份这一安全证据，使用现有 `database_safety` 容器按原事务算法绑定，区别于纯诊断字段。诊断侧文件只是说明材料，安全决策仍从已有完整工件和实时数据重新计算。

首版只计算当前会话涉及的草稿、关系、事务和运行资源，不给业务库每一行维护全局 hash，也不增加后台全库扫描。只有定位需要时才进一步给节点或字段生成摘要；未变的单个节点不能授权绕过整份草稿的旧基线检查。

**限制：** 普通 A→B→A 通常会因修改时间变化被检测；若外部把正文和原时间戳一并恢复，仅看当前快照无法证明期间从未改变。需要这种历史保证时，应由平台提供可靠的单调 revision 或审计。本次明确该边界，不宣称 hash 已解决历史 ABA。

## 3. 统一只读比较与基线错误契约

新增服务层比较模块，供目标读取、接手反馈、重开 preflight 和恢复说明复用。输出包含 `comparison_schema_version`、比较时间、对象身份、`match/stale/unknown`、变化类别、所需旧新摘要和最小下一步。

1. 在同一数据库事务中读取目标草稿及完整关系集合，核对身份、草稿/发布和删除状态。关系超出读取上限、查询超时或数据不可读时，必要证据为 `unknown`，不能当作匹配。沿用受控查询超时，不在等待期间持有本地队列控制锁。
2. 优先从有效审批工件取得 old/new hash 和关系绑定，不把完整会话基线解析变成 pending 审批的新硬性前提。诊断用 payload 摘要缺失仅降低差异说明；核心旧指纹、完整关系或身份无法核实时才阻止自动重开。
3. 对服务级冲突增加携带 `code/details` 的特定异常，复用现有 telemetry 传输封装，不借用编译器异常。建议码为 `draft_baseline_changed`、`draft_relations_changed`、`compiler_binding_changed`；错误明细附 session/backup 标识、旧新指纹、变化类别及重建指引，不返回设计正文。
4. 覆盖发现/目标读取、参数规划、引用修复和进入审批等同类检查点，避免只修 `inspect_edit_context`。现有基线、来源、完整编译及人工审批门禁继续生效。
5. 接手结果增加 `baseline_status=current/stale/unknown` 与检查时刻。基线过旧不应直接拒绝接手，因为接手也用于安全取消旧流程；检查不可用时明确 unknown，不伪称已核实。转交已成功时，后续比较失败仍应返回 `attached=true` 和 unknown，不能把已发生的转交伪装成未发生。
6. 恢复指引复用“查看取消范围 → 明确确认 → 按 fingerprint 取消未执行流程 → 从当前草稿新建会话”。不自动取消、刷新基线、改旧时间戳或迁移审批。只有修改时间变化也保留原 CAS 阻断，明确标注 `revision_only_changed` 后重新规划。

现有通用 `error_code=EditorServiceError` 与补证字段已有实现；本项补的是具体原因和路径，不将旧回执缺字段泛化为当前完全没有错误封装。

## 4. 版本资源失效：实例绑定、预检及独立运行快照

目标是使已启动实例使用的文件在其生命周期内完整可用，同时明确插件与客户端宿主的管理边界。

1. 构建阶段生成运行资源 manifest，列出版本、相对路径及实际文件字节 SHA256。覆盖 server、延迟导入的 Python 模块、UI 脚本、CJS runner、JSON 规则及必要资源，不能只复制入口脚本；只纳入运行依赖，不纳入凭据、业务备份和审批工件。
2. 启动器在完整包可读时，先准备插件自有 `%LOCALAPPDATA%/GxpLowcodeEditor/runtime/packages/<manifest_sha256>/`。先暂存、全量验证、原子启用，再从该目录启动 MCP。后续 UI、编译器及延迟导入使用同一绝对 runtime root。并发准备同一快照去重，失败不接纳半包。
3. 每个 MCP/UI 实例记录 `runtime_instance_id`、插件版本、manifest 摘要和解释器标识，并持有可核验的运行租约。MCP 退出但 UI 尚在时，UI 的版本租约仍保留。运行租约与清理使用共同协调协议，防止清理与新进程启动竞争；首版不自动清理，后续显式清理也必须拒绝活动或无法核实的版本。
4. UI/Node 调用前检查该入口所需资源的存在性与摘要。返回 `plugin_runtime_path_missing` 或 `plugin_runtime_resource_changed`，附实例版本、缺失文件及 `reconnect_required`。预检后发生的文件竞争也保留精确错误，不能退回“窗口进程退出”的笼统说明。
5. 编译适配资源的真实调用前后来源校验继续保留，不用新增 manifest 取代已有校验。已接纳快照的缓存优化只能复用不可变数据；发现变化立即拒绝。
6. 不在运行中自动切到“最新插件目录”，不自动重做 prepare/write。已经缺失文件的旧实例无法凭空重建可信快照，应提示重连到完整版本；不依赖损坏资源且仍可安全运行的本地状态/取消入口继续提供明确恢复路径。

解释器依赖也纳入生命周期管理：绑定实际 Python/Node 路径、版本和必要身份摘要；运行包租约同时声明所用依赖环境。现有 `setup.ps1` 修改共享 `.venv` 前须在共同协调锁下核实租约，活动或无法核实的使用者存在时拒绝原地更新；确需并行升级时另建独立版本环境，旧 UI 继续使用旧环境。Node 调用继续实际探测身份及来源校验。外部手工删除或替换解释器属于可检测后拒绝的故障，不宣称插件能阻止外部破坏。

Codex 何时清理缓存、重载入口不由此仓库控制。运行快照保护已成功启动的实例；尚未启动的缓存入口若被宿主删除，仍需宿主保留入口或重连。交付时文档说明该边界，不承诺源码能阻止宿主清理。

本轮计划不执行安装，也不手工改 Codex 缓存。未来代码验收后仍需用户明确要求，才更新实际安装及连接。

## 5. UI 退出证据与 ready 语义

现有 `process.wait()` 仅等待，不保存退出结果；检测进程消失时只改变查询返回，原 attempt 可继续显示 ready。现场启动器 PID 与实际 UI PID 不同，二者必须分别监测。

1. 每个 startup 保存版本/实例绑定、launcher PID 与创建 token、claimed UI PID 与创建 token、父 PID、ready 时间、phase、心跳时间、正常关闭标记、退出码/时间及观测来源。能取得进程句柄时保留到退出以取得真实退出码；若无法取得，记录 unknown，不能拿启动器退出码冒充 UI 退出码。
2. 按 startup_id 保存追加式事件，并有独立的最新状态快照。事件有 generation、单调序号和观测时间，使用受控状态合并，迟到的旧窗口事件不能覆盖新一次启动。重开生成新 startup_id，原失败记录保持可查。
3. 心跳与退出观测分开。PID 访问失败或创建身份不可核实时返回 `process_state=unknown`；没有心跳不等于进程已死，更不等于未执行。
4. 保持既有 `startup_status=ready` 的“窗口可见且进入事件循环”语义，增量增加 `visible`、`review_ready`、`preview_pending` 等明确字段。ready 回调同步更新当前 phase，避免旧心跳被误读；旧客户端字段保持兼容。审批和执行按钮仍受业务状态、有效审批及门禁控制。
5. 明确区分用户关闭、Python 启动失败、加载异常、观察到异常退出和终止者未知。Job 绑定成功不等于本次被 Job 终止；只有已知证据才记录具体来源。
6. 日志仅保存必要标识、摘要、状态、计数和原因码，不保存 SQL 参数、设计正文、业务数据或凭据。事件预算按固定 schema 限制，重复心跳只维护最新值；故障关键事件不可被后续成功覆盖。历史业务审计及本次材料不参与诊断日志轮换。

MCP 内 daemon 线程在整个进程树被终止后无法继续记录。退出监测必须由实际存活的宿主承担；若观察者也丢失，只能保留最后证据并显示 unknown。

## 6. 实证后修复 UI 与 MCP 的生命周期

建议产品行为：审批 UI 打开后由用户明确关闭；MCP 断开不自动审批、不自动执行，也不应终止 UI。已经由用户发起的执行不因工具连接断开而中断或重复；重连遇到未知结果时先核对。

### 6.1 无业务复现

使用实际 `.venv` MCP SDK、临时回执目录、纯 heartbeat/sleep UI stub 和假事务状态，不使用真实 conversation/session/transaction，不访问业务数据库。记录 client、MCP、launcher、实际 UI 四类进程和实际 Job 关系。

覆盖持续连接、单次调用结束/正常 EOF、服务端未及时退出触发 SDK 清理、客户端异常退出/Job handle 关闭、venv 启动器转发、嵌套 Job 与不允许 breakaway。测试子进程均有固定生存上限及独立清理，异常测试不会留下无限运行进程。

需要实测 Job 创建/绑定结果、UI 是否受同一 teardown Job 约束及断线后的存活结果。官方 SDK 安装不做修改，采用测试夹具和外部观测取得证据。新实验只能证明相同机制可复现，不能倒推原现场具体终止者已证实。

### 6.2 按门禁选择实现

| 实证结果 | 采用方案 | 必要门禁 |
| --- | --- | --- |
| 目标 Windows/SDK 的实际 Job 允许 UI 安全脱离 | 条件 breakaway，保留独立退出监测 | 在真实 SDK 上验证实际 UI 和观察者都脱离会被清理的 Job，观察者持有真实 UI 句柄；覆盖嵌套、拒绝和启动失败；不能仅加 `DETACHED_PROCESS` 或进程组标志 |
| breakaway 不允许、不能核实或仍被清理 | 从 SDK teardown Job 外启动的受控本地 UI host | 确认 host 与 UI 的真实 Job 关系；直接从 MCP `Popen(host)` 不视为解耦；选择用户明确启动或经明确授权配置的宿主入口，不静默安装服务/计划任务 |

host 仅接受当前 Windows 用户的受控 UI 启动、去重和监测请求，验证允许的脚本、版本 manifest、startup_id 和归属，不提供任意命令执行、SQL 执行或审批接口。现有 UI 内人工审批及 writer 协议不迁移为自动后台执行。无活动 UI 时可退出，活动 UI 的租约不因 MCP 断开丢失。

实施先做 stub 并选择最小能通过门禁的方案；若需要独立宿主，其启动/安装方式作为后续明确交付事项。在此之前可使用保持连接的客户端缓解，但不能将其当作生命周期缺陷已修复。两个方案均未完成时，第三项保持未完成，不能仅凭补齐日志验收。

## 7. hash、状态和锁共同驱动安全重开

增加重开只读 preflight：核实会话归属及 owner revision、当前事务/计划指针、有效工件、设计及关系快照、连接目标/账号身份与权限、编译证据的当前适用性、执行状态和旧窗口身份。账号身份单独核实，不把 host/port/database scope 或相同权限当作同一账号。

新事务在 prepare 阶段从已核验的数据库连接读取实际认证主体（例如 `CURRENT_USER()`），与目标环境一并冻结到现有已签名的 `database_safety`；重开和执行时与当时冻结值比较，不能拿当前账号与自己比较。旧合法工件缺该字段时不补签、不一概阻断：仍严格验证其原有 scope、账号模式、已签名 grants、审批等绑定，标注 `principal_verification=legacy_grants_only`，不宣称完成独立账号身份对比；已知账号漂移或原绑定不满足则要求新计划。新字段的验证器及 writer 采用增量兼容规则。

重开比较所需的当前数据按目标定向读取；草稿和关系取同一事务视图。preflight 成功只是当时适用，最终执行仍由执行锁、SQLite claim、执行标记、数据库行锁、旧内容/关系及时间 CAS、审批 HMAC、影响行数和写后复核决定。编译来源按现有就绪/来源检查复用有效证据；检查失败或必需证据不全返回 unknown。

| 状态/证据 | 处理 |
| --- | --- |
| 旧窗口身份已核实且存活、心跳正常 | 返回已有窗口，不重复启动 |
| 实际 UI 已退出；当前事务仍待审批且无任何执行标记；所有必要身份/指纹/权限/来源检查匹配；相关锁闲置 | 同一 transaction 重开 UI；有效未过期审批按原协议保留，过期重新取得；不自动批准或执行 |
| 仅修改时间变化，payload 一致 | 返回 revision_only_changed；不改旧 CAS 条件，重新规划/审批 |
| 正文、关系、目标状态、归属、需求、账号/权限或编译绑定改变 | 旧计划不能继续执行；展示变化和取消/重建路径，不自动取消或覆盖 |
| 必需数据不可读、工件损坏或缺关键绑定、PID 身份不能核实 | 返回 unknown 与补查路径；可只读查看已有工件，禁用执行；不自动终止、重开执行或标记成功 |
| executing、execution_started/executed、提交回执丢失或执行记录矛盾 | 禁止原事务再次执行，先取得执行锁并核对结果 |
| 核对后当前草稿及关系匹配候选 | 说明“当前快照与候选一致”，按既有协议核对本地状态；不重复写，不仅凭 hash 宣称该事务实际提交 |
| 核对后匹配原状 | 说明“当前为原状”；不宣称历史从未执行；结束旧尝试后如需编辑应重新规划 |
| 当前与前后均不匹配 | 保留当前数据，报告变化；不得自动恢复覆盖 |
| 已知 saved/saved_state_pending 后又变回原状 | 归为保存后的变化，不误判为从未写入 |
| 已完成事务再次查询 | 返回历史回执及核验范围；未实时读取时明确不代表当前草稿仍相同，禁止再次执行 |

结果核对增量返回 `verification_scope`、`current_matches_baseline/candidate`、`execution_outcome` 和 `commit_evidence`，并将它们作为带 schema 的核对回执持久化到本地状态，贯穿 `get_write_status`、`verify_saved_draft`、完成及历史查询。不能让首次 recovery 说明“提交归因未知”，下一次查询又仅从 `state=saved` 推出 `executed=true`。既有业务状态保持兼容；`executed` 布尔仅表示有确认的执行完成证据，未知时返回 false 并明确 `execution_outcome=unknown`、原事务不可重试，界面/技能不能把 false 解释成“从未执行”。历史缺少归因证据时也不倒填确认。区分“当前结果匹配”与“已证明本次提交”，不能用新增 hash 绕过现有未知执行恢复规则。

### 队列单独处理

现场是 queue UI，不能只测试单事务窗口。首版闭环“已确认实际退出”的队列重开；存活但卡住的队列继续拒绝自动终止，提示关闭前确认无执行并按现有处理路径恢复，不直接放开当前 queue 回收白名单。

新增独立短时 queue control 协议与 revision/generation，队列成员写入、转交、advance 和 execution claim 遵守同一协调规则。它与窗口终身持有的 `approval_queue_lock` 分开。统一锁顺序在实现设计中先固定并通过并发测试；本地锁采用非阻塞失败返回，不持有 queue control 跨业务查询或等待用户。

已退出队列重开时，读取包含成员、顺序、owner revision、当前事务及状态的快照，按稳定顺序核对相关执行/窗口锁，逐项 preflight；耗时读取后重新核对 queue revision、指针和执行标记，快照变化即拒绝旧结果。旧 queue/window 锁确认释放后启用新 generation，由子 UI 在取得自己的窗口锁后再核验 generation。新加入项经过正常流程，不沿用旧快照许可。

最后重验和启动交接必须原子化：耗时 preflight 在控制锁外，随后在统一 launch/queue control 临界区重读 revision、成员、指针及执行标记，确认相关非阻塞锁检查后，原子保留新 generation 和唯一启动令牌。并发重开、advance 与 execution claim 都遵守该令牌；子 UI 取锁后的再次核验是第二道门禁。启动失败仅按本次 generation 作 CAS 释放保留；超时仍无法确认子进程状态时保留未知状态，不能仅凭超时再启动第二个窗口。

已完成且已核验的项可以展示；结果不明项只能核对，不能作为待执行项继续；待审批项使用各自有效事务。重开不能重做已完成项，也不能因其他队列项的 hash 一致而跳过当前项检查。

## 8. 实施批次、测试与验收

按下列五个独立提交推进；每批包含对应回归和文档，失败时只扩大与失败相关的验证。计划阶段不运行或宣称这些测试已通过。

| 批次 | 实施与主要位置 | 验收证据 |
| --- | --- | --- |
| A：基线契约与比较器 | 新比较模块；`service.py`、`telemetry.py`、`hashing.py`；业务状态及签名不变 | 成功/失败经实际 MCP 输出转换；同值、仅时间、正文、关系及 unknown 分类；旧基线继续阻断；接手仍可用于确认取消 |
| B：资源稳定性（高优先级） | 运行 manifest/快照模块、`start_mcp.ps1`、UI/编译资源预检 | 暂存失败不接纳；并发准备同包去重；活动版本不可清理；模拟缓存文件缺失时自有快照仍可用；损坏快照明确拒绝，不混版本 |
| C：退出观测及 SDK stub（高优先级） | `ui_launch.py`、`approval_app.py`、`abort_session_app.py`、纯测试夹具 | 真实 UI/launcher 分离；首次失败留存；ready 与 phase 对齐；Job 创建/绑定和断线结果有实证，未知退出原因不冒充已知 |
| D：生命周期修复 | 依据 C 选择条件 breakaway 或独立 host；实现版本绑定及监测 | 正常 EOF、超时清理、异常断线后 UI 按策略存活；客户端已退出后 UI 再异常退出仍能留存真实退出证据；用户关闭正常回收；执行中断线不产生二次执行；失败分支明确报告能力不足 |
| E：安全重开与恢复 | `service.py`、`recovery.py`、`state.py`、`execution_lock.py`、queue UI | dead queue/单事务可安全重开；并发转交/入队/执行导致安全重验或拒绝；旧签名兼容；未知结果不重复执行 |

B、C 优先排查运行稳定性，可与 A 独立推进；D 依赖 C 的实证，E 在比较器和新运行/窗口身份契约稳定后集成。可以先合入已验收的小补丁，但三项整体交付必须满足全部门禁，不能用某一批通过代表全部修复。

必要场景矩阵：

- 内容：完全一致；只有时间变化；data/JS/C# 分别变化；关系增删改/软删/重排；Unicode；只有目标发布/删除状态变化；关系读取不完整；数据库不可用。
- 工件与授权：历史合法工件缺诊断新字段；损坏 baseline 但合法 pending 工件可用；statement/transaction 篡改；审批过期；需求/归属/账号/grants/compiler 漂移；preflight 后再次变化。
- 运行资源：UI 脚本、runner、延迟导入资源缺失/改变；启动中版本切换；两个版本并存；MCP 已结束但 UI 仍用旧包；快照复制/校验失败。
- 进程：启动失败；正常关闭；ready 后异常消失；launcher 与 UI PID 不同；PID 重用；进程查询被拒；心跳过旧；旧事件迟到；观察者与服务端同时结束；Job 绑定失败/嵌套/不允许脱离。
- 恢复：单窗口与 completed+pending 混合队列；并发重开/入队/转交/执行 claim；活着的卡住队列拒绝自动终止；提交成功但回执丢失；当前匹配候选但提交归因未知；匹配原状但历史未知；设计匹配而关系不匹配；保存后被改回；ABA 可检测与不可检测边界。未知提交→匹配候选恢复→重连查询→完成→历史查询的完整链路须持续保留核验范围与归因，原事务始终不能重执。

复用现有 `test_context_service`、`test_session_release`、`test_ui_launch`、`test_writer`、`test_recovery`、`test_recovery_service`、`test_conversation_tools` 等定向回归；按实现新增比较器、运行包和真实 SDK 生命周期集成夹具。Windows Job 集成必须在目标 Windows/SDK 环境实际运行；被跳过或仅 mock 通过不算该项验收。

所有自动测试使用合成数据、临时 state/工件和有限生存 stub；不重新使用用户实际 ID，不重新批准或执行业务 SQL。若需验证真实 MySQL 行锁/CAS，以隔离测试库和合成表为单独验收，不用生产草稿代替。

最终门槛：原三类故障均有可区分响应；无自动审批/执行/取消、无未知结果重试、无旧证据放行、无版本混用；已完成项不重复执行。只读状态查询不新增业务写入，诊断记录失败不被解释为业务成功。新增 preflight 不全库扫描，性能单独报告读取次数、耗时和故障路径，不借旧微基准宣称本轮提速。
