# GXP Low-Code Edit

## Activation and scope

- First activation requires the current user message to invoke `$gxp-lowcode-edit` or its plugin-qualified form. Preserve `policy.allow_implicit_invocation: false` in `agents/openai.yaml`. Before activation, readonly diagnosis, a proposal or “continue/apply the plan” does not authorize business tools, including `editor_status`; explain the explicit invocation required and stop that editing path.
- After activation, continue the same dialogue's authorized draft without another invocation: inspect, revise under fixed expectations, reopen requested review, verify, recover and finish. Another dialogue, a new target or revoked authorization is outside that scope. An explicit multi-action queue covers only its identified targets.
- Write works independently; Look, complete diagnosis, proposed fixes and `handoff_ref` are optional. Reuse relevant evidence when environment, draft fingerprint and complete target parameters match the backup. Investigate gaps or contradictions directly or through Look readonly tools; revise unsupported conclusions. A proposal is input, never a mandatory fix or approval.
- Activation authorizes planning and opening the formal local approval application. Open it when ready without another chat confirmation or a standalone preview. Only its human user approves SQL and confirms execution.

## Local database settings

An explicit request to view/change Look/Write settings uses `database_settings` without a conversation or edit session and does not activate business editing. Read non-secret `status`; use `open` for manual settings/password entry. For model-assisted `update`, pass only user-supplied non-secret fields and `expected_revision` from that status. Never guess endpoints or pass passwords/connection strings. The user's clear configuration instruction already authorizes that local change. Read [database-settings.md](references/database-settings.md) for fields, active-session handling and the standalone launcher.

## Normal draft workflow

1. Call `create_conversation(label)` once; keep its `conversation_id` in this dialogue and pass it on every later business-editor call. Call `begin_edit_session` for the requested action code/RefId, optionally with verified `handoff_ref`. Confirm the active unpublished draft, immutable backup, exclusive ownership, complete element coverage and compiler binding. Assess `evidence_candidates`; never automatically choose the newest or exhaust pages. A blocked entry creates no session: retain its state and follow the matching procedure.
2. Find unknown groups/nodes with `find_edit_nodes` against the session backup; inspect exact targets with `inspect_edit_context` unless matching context was returned at entry. Follow [targeting rules](references/targeting-and-source.md#怎样确定要修改的元件), complete-old-value guards and current `supported_operations`. Prefer `set_parameter` for existing parameters; use `set_array_item` only with a verified native row id/key. `replace_params` replaces both complete dictionaries. Fill template `required_inputs`; continue template pages with the identical target list. For callbacks verify the real component, payload, visible inputs and execution path. Use native IF nodes for branch-specific effects.
3. Before generation, fix `review_spec` from the original request and confirmed rules: quoted `source_text`, exact targets, preserved behavior and distinguishing scenarios. Use `scope_policy="strict"`; `manual_review` requires explicit user basis and a new revision when policy changes. Include appropriate filter, AND/OR and output assertions. Never derive expectations from the candidate or weaken a failed expectation. Translate applicable old proposals through current templates; develop missing fixes from supported evidence. Batch this draft's confirmed operations into one `plan_canvas_patch` and one approval transaction. `generation_mode="full"` is the default; honor the user's mode, or choose incremental/auto based on actual scope. Report the actual mode, scope and reason before approval.
4. Keep `response_detail="summary"`; inspect `review_status`, `review_summary`, `review_issues` and `ready_for_approval`. Use `read_plan_review` for selected evidence. `open_plan_review` is only for an explicitly requested standalone preview, including after a failed plan. `no_changes=true` ends this planning attempt without approval; it neither cancels nor authorizes approving an older plan. Compilation/tool failure before completion creates no plan. A returned failed plan remains blocked: repair the whole batch from the immutable baseline under the same expectations. Omitted specifications inherit them; old reports without a scope policy require replanning.
5. When `ready_for_approval` and `write_ready` are true, call `prepare_write` directly and report the formal approval window is opening. It independently rechecks the current draft, candidate and compiler/business evidence. `window_starting` means pending startup; follow `next_action`/`poll_after_ms` and [status guidance](references/session-workflows.md#approval-status-and-polling) without opening a second window. Waiting for human review is not execution progress or permission to approve.
6. Human approval covers actual SQL plus bound parameters and target row. Canvas data/JS/C# share one main-row UPDATE and one approval; additional row statements are reviewed separately, even when templates match. Final save confirmation executes already-approved statements. The save worker verifies committed draft/relations against approved hashes and atomically releases the session. `get_write_status` with both `verified=true` and `session_released=true` confirms completion. Otherwise verify with `verify_saved_draft`, then `finish_edit_session` after verification; use recovery for uncertainty. A historical `saved_verification` proves only its recorded snapshot.
7. Ask the user to inspect the canvas and manually republish each action: list name, code and owning form/public action from `publication_targets`. Use `get_edit_queue` to report all completed verified saves even if a later item fails; exclude other saves. Draft saving proves neither publication nor runtime behavior.
8. After verified release, compare this investigation with Look's graph and persist the result through `record_graph_review` using its revision. Reuse saved `review_state` across status calls and queue summaries. Ask once only for concrete confirmed additions/corrections; a refusal stays declined. No difference needs no question. Pending publication stays pending. Graph updates require separate explicit consent and a complete current case snapshot merged with valid sibling supports; follow the [graph workflow](references/evidence-and-performance.md#review-looks-graph-after-a-completed-write). Failed, cancelled, unchanged or unverified saves do not trigger it.

## Required boundaries

- Edit only an unambiguous existing unpublished draft. Missing/corrupt backups, unknown `elementKey`, unsupported dynamic plugins, duplicate keys or invalid nesting block editing. Never create/publish/delete designs, execute arbitrary SQL or supply generated JS/C#, persistent keys or published identifiers as operations. Native generators own those artifacts and keys; supported batch-local aliases are not persistent keys.
- Compiler workspace/commit, bridge, rules, adapter, registry and version bindings must match. Canvas validation must be exactly valid; independently regenerated JSON/code/relations and approved hashes must agree. Required action code must be nonblank and `relation_data` an object. Nonblank candidate C# must compile completely before planning and again before approval; missing checkers, timeouts, drift or errors block. Local development compilation does not prove production readiness.
- Check every JS group in every generation mode, including unchanged source. Compare old undeclared references, implicit `arguments`, reserved platform writes/declarations, incomplete event bindings and ParamInput mismatches against the immutable baseline using the compiler's located evidence. Proven old findings stay nonblocking and `unverified`; report them without automatically widening scope or rewriting callbacks/types. New occurrences, changed declarations and newly reachable bad references block. Syntax, native signatures, exact generation and complete C# checks remain mandatory. Explicit user acceptance rules still apply even if the baseline fails them. Read the compiler contract before interpreting such findings; never change generation mode to evade a check.
- Preserve exact target ownership, draft concurrency, account/index gates, pinned grant fingerprints, one affected row per statement and signed human approval. Prefer least privilege; never select `shared_unrestricted` without the user's explicit local configuration confirmation.
- Never approve/execute for the human, bypass expired/tampered approval, clear a live executor, call backend save/publish endpoints, connect Redis or write/delete DLL/PDB. Cancellation and local release require the dedicated inspected scope and explicit user agreement described in session workflows; they are not automatic cleanup. Restore is a new approval transaction. Uncertain outcomes need recovery or confirmed local release retaining its unverified result and audit history.
