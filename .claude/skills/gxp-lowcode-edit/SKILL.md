# GXP Low-Code Edit

## Explicit invocation gate

- First activation requires that the current user message explicitly invokes `$gxp-lowcode-edit` or its plugin-qualified form. Keep `agents/openai.yaml` at `policy.allow_implicit_invocation: false`.
- Before activation, a readonly diagnosis, proposed plan or "continue/apply the plan" is not an invocation. Do not call `editor_status` or other business-editing tools; explain the required explicit invocation and stop the editing path. An explicit request to view/change local database settings may use only the separate `database_settings` entry below, without activating editing.
- After activation, the same dialogue may continue its authorized draft: query status, revise its candidate under the fixed expectations, reopen requested review, verify, recover or finish. Do not demand another invocation for each continuation. A new target, another dialogue or revoked authorization is not covered; do not silently begin another draft. An explicitly requested multi-action queue covers only its identified targets.
- Write works independently; prior Look use, a complete diagnosis and `handoff_ref` are optional. First check the current dialogue and available evidence for relevance, completeness and applicability to the current draft. The readonly plan is only an input candidate, never a prerequisite or a mandatory fix. Verify reused target evidence against the session backup, including draft identity, content fingerprint and complete target parameters. Fill gaps or resolve contradictions through focused analysis or Look's readonly tools; do not require the user to start Look or produce a complete handoff.
- Activation authorizes guarded planning and opening the local approval application. Open the formal approval directly, without another chat confirmation or standalone preview step. Only the human in that application approves statements and confirms execution.

## Local database settings

For an explicit user request to view/change Look/Write database settings, use local `database_settings` without a conversation or edit session, even before database configuration. `status` reads non-secret settings without a connection; `open` launches the shared settings window for manual edits and hidden password entry. The same window is available through `python scripts/database_settings.py` from the plugin directory (`python3` on macOS/Linux).

For a model-assisted change, read `status`, then pass only user-supplied `host`, `port`, `database`, `look_user` and `write_user` in `changes`, with that status revision as `expected_revision`, to `update`. Never guess an endpoint or pass passwords/connection strings. Use `open` when a password is needed. A clear user instruction already authorizes the requested local configuration change; do not add another confirmation. See [database-settings.md](references/database-settings.md) for validation, active-session handling and shared-profile behavior. This entry never grants business-editing, saving or approval authority.

## Read only what the operation needs

- Before constructing operations, read the target-location section of [targeting-and-source.md](references/targeting-and-source.md) once per dialogue. Its source sections are needed only for source inspection. Current ActionDesign evidence identifies the business node; repository searches do not.
- Read the relevant operation section of [patch-schema.md](references/patch-schema.md) and the applicable sections of [business-review.md](references/business-review.md). Reuse already-read sections while their source binding is unchanged.
- For existing diagnosis evidence, optional `evidence_candidates` / `handoff_ref`, operation-template continuation, batch error repair or a measured performance issue, read the relevant section of [evidence-and-performance.md](references/evidence-and-performance.md). Reuse supported findings, proposed fixes, preserved behavior, scenarios and returned `edit_context` when they apply. Adequate evidence should reduce repeated searches; it must not block necessary investigation. If evidence is incomplete, stale or contradictory, analyze the affected question directly or use Look's readonly tools, and revise the old cause or proposal when new evidence supports it. Records may contain only the symptom and evidence, with no confirmed cause, fix or target snapshot. Cross-dialogue records require current scope confirmation and grant no inherited authorization or approval.
- For new or changed callbacks, read event contracts in [frontend-compiler-contract.md](references/frontend-compiler-contract.md), inspect native component signatures and verify the exact page component and binding execution path. Read other compiler sections only for a readiness discrepancy, compilation failure or interpretation of generated-code review.
- Existing event parameter metadata mismatches also require baseline comparison. If the binding identity and complete callback declarations are unchanged, report the old mismatch for the user's decision and continue; do not change `value`, its references or `string` to `any` merely to pass the checker. New bindings or changes to those declarations must satisfy the event contract.
- Apply the same baseline rule to old implicit `arguments`, reserved platform declarations/writes, incomplete event binding evidence and ParamInput display/code mismatches. Read the tool's located diagnostics and comparison evidence before proposing a fix. An unrelated edit never authorizes changing old declarations, references, types or business behavior. If generation or a required check cannot complete, explain that concrete limitation; do not call the old code a newly introduced error or automatically expand the repair. Explicit user acceptance assertions still apply even when the baseline also fails them.
- Use [session-workflows.md](references/session-workflows.md) only for reference repair, restore, recovery, dialogue transfer or multi-action queues. Use [safety-contract.md](references/safety-contract.md) for account or approval details that need clarification. Do not load all references for an ordinary edit.
- For AI cancellation or local release of an old workflow, follow [session-workflows.md](references/session-workflows.md): inspect the exact scope and meaning, obtain the user's explicit agreement, then call the matching dedicated tool. Cancellation invalidates unexecuted work; local release archives an unverified flow without checking its business result. Neither authorizes saving or publishing, and neither is automatic error cleanup.

Batch independent evidence reads after their prerequisites are known. Keep session mutations, planning, approval and recovery sequential. Session entry returns `supported_operations`, `source_repositories` and `readiness_snapshot`; reuse them instead of another status call. `editor_status` defaults to `probe_runtime=false`; request `true` only to diagnose SDK/reference availability. Reusing evidence never replaces mandatory checks inside the tools.

## Normal draft workflow

1. Call `create_conversation(label)` once. Retain its `conversation_id` locally to this dialogue and pass it on every later editor tool call. Never reuse another dialogue's marker.
2. Call `begin_edit_session` for the requested action code or RefId, passing a verified readonly `handoff_ref` when available; omit it otherwise. Normal entry and same-session retries without a reference return bounded optional `evidence_candidates` for this exact action and environment. Assess their symptom, source and verification summaries; explicitly read a relevant record if useful, and follow `next_read` only when more candidates are needed. Never automatically select the newest record or exhaust every page. Lookup failure does not block independent editing. Confirm an active unpublished draft, immutable backup, exclusive ownership, complete element coverage and compiler source binding. Compare reused evidence with that backup. A `diagnosis_only` record carries historical findings but no current target snapshot: locate and inspect current targets normally. For stale, missing or divergent records, follow `stale_reason` / `refresh_scope` or the ordinary inspection path; a refreshed export is optional, and no new session or plugin restart is required. Match configured source repositories with readonly source evidence when both are relevant. A blocked entry is not a new session: retain its returned state and use the appropriate [session procedure](references/session-workflows.md), without repeatedly retrying entry.
3. Check supported operations. For verified target keys call `inspect_edit_context(session_id, targets=[{group_key,node_key}], conversation_id)` for 1–10 exact nodes unless matching context was returned at entry. It checks ownership, draft fingerprint and compiler binding, and returns backup identity, complete native parameters, row, parents, visible variables, registry contract and incomplete safe operation templates. Fill their required inputs; continue templates with `next_operation_cursor` and the identical target list. Source bodies are not parsed; inspect source only when that structured contract is insufficient. For an existing parameter prefer `set_parameter`; use `set_array_item` only when advertised and the row has a verified native `id`/`key`. Follow complete-old-value and synchronized ParamInput rules. `replace_params` still replaces both complete dictionaries. For events verify payloads, visible callback inputs and execution path; use native IF nodes for branch-specific side effects.
4. Before generation, fix `review_spec` from the user's original request: quoted source, exact targets, unchanged behavior and distinguishing scenarios. When an applicable proposal exists, translate its `change_spec.changes` through current templates into operations, and map available `user_request`, `preserve` and `scenarios` to review requirements and cases as described in [evidence-and-performance.md](references/evidence-and-performance.md). If no complete proposal exists, develop one from the available evidence and any necessary focused investigation; revise older causes or fixes when justified, explain the evidence and preserve confirmed acceptance details. New plans default to `scope_policy="strict"`, requiring targets on every requirement and blocking extra changes. Use `manual_review` only with explicit user evidence; policy changes require a new revision and new basis. Include relevant static assertions for filters, AND/OR and outputs. Never derive expectations from candidate output or weaken a failed expectation. Batch confirmed operations for this draft into one `plan_canvas_patch`, then one `prepare_write` and approval transaction/window; do not submit separately for each component or operation. Its `generation_mode` is `full` by default; honor the user's explicit `full`, `incremental` or `auto` choice. Without an explicit preference, retain that default or choose incremental for a small affected scope or auto to let the tool decide from actual changes/dependencies. Before approval report the actual mode, affected scope and reason. See [frontend-compiler-contract.md](references/frontend-compiler-contract.md) for mode boundaries.
5. Keep the default `response_detail="summary"` for planning and preparing approval. Read `review_status`, `review_summary`, `review_issues` and `ready_for_approval`; use `read_plan_review` only for the relevant section or issue ID. Full evidence remains in the bound report and formal approval UI. Do not call `open_plan_review` in the normal or failed-plan workflow; a standalone preview is available only if the user explicitly requests one. `no_changes=true` stops this planning path without new approval; it does not cancel an existing plan, and never authorizes sending that old plan to approval automatically. Compilation/tool errors before completion also create no plan. A returned failed plan exists but is blocked: read its failure evidence without opening a window, explain the mismatch and fix operations under the same expectations. Omitted specifications inherit those expectations. Summarize visible rules and unresolved verification; do not repeat full code, parameters or hashes in chat. Old reports without scope policy remain readable, but require replanning before new approval.
6. Once `ready_for_approval` and `write_ready` are true, call `prepare_write` immediately. Report that the formal approval window is opening; skip standalone preview and another opening confirmation. The tool rechecks current draft, compiler binding, complete candidate and bound business evidence before creating a transaction. Follow its bounded startup result: `window_starting` is pending, not an opened window; check status without starting another window. A startup error follows the [recovery procedure](references/session-workflows.md), preserving the existing transaction. Unverified evidence remains available for human judgment, and is never reported as passing.
7. The local approval application approves actual SQL statements, not canvas operations: the draft's data/JS/C# share one main-row UPDATE and one SQL approval. Additional SQL is reviewed separately by SQL plus bound parameters/target row, never merged merely because templates match or automatically approved as a batch. Final save confirmation executes the approved transaction; it is not another SQL approval. Its save worker immediately re-reads the committed draft and relations, compares the exact approved hashes, and atomically records verification and releases the session before showing success. Poll only with `get_write_status`: `verified=true` and `session_released=true` confirm completion. If a saved transaction remains unverified, call `verify_saved_draft`, then `finish_edit_session` only after verification; uncertain results follow recovery. A stored `saved_verification` proves the committed snapshot at its recorded time, not later platform edits or publication. After session completion, explicitly tell the user which actions to republish: list each action's name, code and owning form (or public action) from `publication_targets`, and ask them to inspect the canvas and manually republish those actions. For multiple actions, summarize all completed, verified saves; use `get_edit_queue` for the cumulative queue list, including when a later item fails. Exclude pending, failed and unverified saves. Draft saving does not establish publication or runtime completion; never report these actions as already published.

8. After a save is verified and the session is released, review whether this investigation adds or corrects anything in Look's relation graph, even when Write was used without Look. Completion responses expose `look_graph_review` as a reminder to compare, not an instruction to ask unconditionally or permission to write. Reuse this dialogue's evidence and current graph information; read only the relevant existing relations if needed. No existing relation may mean an addition; an existing relation may need supplementation or correction. If confirmed, recordable differences exist, show the specific additions/corrections and ask once: “是否根据本次排查结果，新增或修改 Look 关系图？” Wait for explicit consent before changing the graph. If the existing graph is accurate and there is no difference, say it needs no update and do not ask. Missing tools or unverified evidence are unknown, not proof of an empty graph. For batches, combine completed transactions into one review/question; do not repeat it on status polling or after the user declines. Failed, cancelled, unchanged and unverified saves do not trigger this step. See the post-write graph section of [evidence-and-performance.md](references/evidence-and-performance.md) for comparison, consent and draft/publication evidence boundaries.

## Required boundaries

Failed batches return bounded phase/operation/location diagnostics and independent preflight issues. Use their `refresh_scope`, repair the whole batch under the same `review_spec`, and resubmit from the immutable session baseline; do not stack failed candidates or send an older plan automatically. Tool `trace_id` and stage timings explain where time was spent; preparation caches never replace fresh independent generation or complete C# compilation. See [evidence-and-performance.md](references/evidence-and-performance.md) for those conditional details.

- No published, deleted or newly created design, ambiguous active draft, missing/corrupt backup, unknown `elementKey`, unsupported dynamic plugin, duplicate key or invalid nesting.
- Compiler commit/workspace, bridge, rules, adapter, registry and version bindings must match. Canvas validation must be exactly valid; independently regenerated JSON/code/relations and candidate hashes must agree. Every action type must have its required nonblank generated code, and `relation_data` must be an object. Never supply generated `js_code`, `csharp_code`, SQL, new persistent node keys or published identifiers as canvas operations. Supported batch-local `node_alias` references let the native compiler generate actual keys; use `insert_in_block` to fill a newly created IF within one plan as described in [patch-schema.md](references/patch-schema.md).
- Nonblank candidate C# must compile locally before planning and again before approval. Unavailable checker, timeout, reference drift or compile failure blocks the candidate. Development references prove local compilation only; `production_ready` stays false without separate deployment/runtime evidence.
- Every mode checks all JS groups, including unchanged saved source. A small edit or old group never exempts checks. For undeclared references, implicit event arguments and reserved platform writes/declarations, block newly introduced findings; compare concrete occurrences against the immutable pre-edit source. Existing findings become nonblocking `baseline_diagnostics` with located source evidence and `unverified` status, even in regenerated groups. Unchanged canvas field inconsistencies and reserved declarations appear in `canvas_diagnostics`; incomplete unchanged bindings appear in `checks[].binding_issue`. Report unrelated old problems and let the user decide whether to repair them; do not expand this edit automatically. Statically proven unreachable references become nonblocking `unreachable_diagnostics`. A formerly unreachable reference made reachable is a new problem. See [frontend-compiler-contract.md](references/frontend-compiler-contract.md) for evidence limits; titles, comments or missing local callers do not prove deprecation. Complete JS syntax, native generated-signature consistency and complete candidate C# compilation remain mandatory. Incremental generation regenerates changed groups and dependencies while preserving other saved source; auto selects the mode before checks. Never switch modes to evade failures. Static structured variable/action diagnostics remain advisory. Reserve the exact variable names `inbiz` and `Inbiz`: do not introduce declarations or overwrite the platform entry/mount. Native factory input and normal `inbiz(...)` calls remain valid; distinct names such as `innerInbiz` and `pageInbiz` are allowed. Explicit reference repairs use the dedicated full-generation workflow.
- Index and account-safety gates, pinned matching shared-account grant fingerprints, exact target ownership, draft concurrency, one affected row per statement and signed human approval remain mandatory. Prefer least privilege. Privileged `shared_unrestricted` mode requires the user's explicit local configuration confirmation; do not enable it from a model decision.
- Never approve or execute for the human, bypass an expired/tampered approval, clear live execution, silently discard an uncertain workflow, call backend save/publish endpoints, connect Redis, or write/delete DLL/PDB. Restore uses a new approval transaction; uncertain results require recovery or explicitly confirmed local release, never guessed success or automatic rollback. Local release must retain its unverified result and audit history.
