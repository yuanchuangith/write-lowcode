# GXP Low-Code Edit

## Activation and scope

- First activation requires the current user message to invoke `$gxp-lowcode-edit` or its plugin-qualified form. Preserve `policy.allow_implicit_invocation: false` in `agents/openai.yaml`. Before activation, readonly diagnosis, a proposal or “continue/apply the plan” does not authorize business tools, including `editor_status`; explain the explicit invocation required and stop that editing path.
- After activation, continue the same dialogue's authorized draft without another invocation: inspect, revise under fixed expectations, reopen requested review, verify, recover and finish. Another dialogue, a new target or revoked authorization is outside that scope. An explicit multi-action queue covers only its identified targets.
- Write works independently; Look, complete diagnosis, proposed fixes and `handoff_ref` are optional. Reuse relevant evidence when environment, draft fingerprint and complete target parameters match the backup. Investigate gaps or contradictions directly or through Look readonly tools; revise unsupported conclusions. A proposal is input, never a mandatory fix or approval.
- Activation authorizes planning and opening the formal local approval application. Open it when ready without another chat confirmation or a standalone preview. Only its human user approves SQL and confirms execution.

## Local database settings

An explicit request to view/change Look/Write settings uses `database_settings` without a conversation or edit session and does not activate business editing. Read non-secret `status`; use `open` for manual settings/password entry. For model-assisted `update`, pass only user-supplied non-secret fields and `expected_revision` from that status. Never guess endpoints or pass passwords/connection strings. The user's clear configuration instruction already authorizes that local change. Read [database-settings.md](references/database-settings.md) for fields, active-session handling and the standalone launcher.

## Normal draft workflow

1. Call `create_conversation(label)` once; retain its `conversation_id` and pass it on every later business-editor call. Enter the requested action code/RefId with `begin_edit_session`, optionally with verified `handoff_ref`. Confirm the unpublished draft, immutable backup, ownership, element coverage and compiler binding. Assess bounded `evidence_candidates` only when useful; do not automatically choose the newest or exhaust pages. A blocked entry creates no session; follow its matching recovery branch.
2. Locate unknown nodes with `find_edit_nodes`, then use `inspect_edit_context` on exact targets unless entry already supplied matching context. Follow [targeting and value-reading rules](references/targeting-and-source.md): default summaries, focused `parameter_paths`, unchanged `guard_ref` templates and `read_edit_value` only for needed exact values. Read the relevant operation schema and real callback contract. Prefer `set_parameter`; branch-specific effects use native IF nodes.
3. Fix `review_spec` from the original request: quoted `source_text`, exact targets, preserved behavior and distinguishing scenarios. Use `scope_policy="strict"`; follow [business acceptance](references/business-review.md) for assertions and justified `manual_review`. Follow [readability](references/readability.md): native variable/value displays, complex conditions defined as variables, cohesive child actions. Preserve evaluation, lock and write order. Build one candidate or append with `append_to_plan_id`; approve once. Reuse entry budgets and declared aliases. Default generation is `full`; honor the user's mode and report actual scope and reason. Never weaken expectations to fit a candidate.
4. Keep `response_detail="summary"`; inspect `review_status`, `review_summary`, `review_issues` and `ready_for_approval`. Read selected evidence with `read_plan_review`; never exhaust pages automatically. `open_plan_review` requires an explicit standalone-preview request. `no_changes=true` ends this planning attempt without approval: a fresh empty session is released; `session_released=false` retains existing work and does not authorize an older plan. A compilation failure creates no plan; a returned failed plan stays blocked. Repair the complete batch from the immutable baseline under the same fixed expectations; see [result routing](references/business-review.md#read-results-and-route-the-next-step).
5. When `ready_for_approval` and `write_ready` are true, call `prepare_write` directly and report that the formal approval window is opening. Follow `next_action`/`poll_after_ms` and [status guidance](references/session-workflows.md#approval-status-and-polling); `window_starting` is pending startup, not a reason to open another window. Yield while waiting for human review.
6. The human approves actual SQL with bound parameters and target row. Canvas data/JS/C# share one main-row UPDATE; additional statements need their own approval. Final confirmation executes approved statements. `get_write_status` with both `verified=true` and `session_released=true` confirms completion. Otherwise follow `verify_saved_draft`, verified `finish_edit_session` or the matching recovery branch. A historical `saved_verification` proves only its recorded snapshot.
7. Ask the user to inspect the canvas and manually republish each action: list name, code and owning form/public action from `publication_targets`. Use `get_edit_queue` to report all completed verified saves even if a later item fails; exclude other saves. Draft saving proves neither publication nor runtime behavior.
8. After verified save and release, follow [post-write graph review](references/post-write-graph-review.md) and persist its outcome through `record_graph_review` with the current revision. Reuse saved `review_state`; no difference needs no question, a refusal stays declined, and unpublished facts stay pending. Graph mutations require separate explicit consent and a complete current case snapshot merged with valid sibling supports under CAS. Failed, cancelled, unchanged or unverified saves do not trigger this workflow.

## Required boundaries

- Edit only an unambiguous existing unpublished draft. Missing/corrupt backups, unknown `elementKey`, unsupported dynamic plugins, duplicate keys or invalid nesting block editing. Never create/publish/delete designs, execute arbitrary SQL or supply generated JS/C#, persistent keys or published identifiers as operations. Native generators own those artifacts and keys; supported batch-local aliases are not persistent keys.
- Compiler input paths, bridge, rules, adapter, registry and version bindings must match. Git commit/branch changes and unrelated documents are audit metadata, not invalidation triggers. Canvas validation must be exactly valid; native-produced JSON/code/relations and approved hashes must agree; unchanged output from the same source-checked compiler call is reused. Required action code must be nonblank and `relation_data` an object. Nonblank candidate C# must compile during planning. Approval reuses bound generation/build evidence when candidate/source/reference bytes match; it does not regenerate or rebuild unchanged candidates. Changed references require a fresh successful build; missing checkers, timeouts, drift or errors block. Local development compilation does not prove production readiness.
- Check every JS group in every generation mode, including unchanged source. Compare old undeclared references, implicit `arguments`, reserved platform writes/declarations, incomplete event bindings and ParamInput mismatches against the immutable baseline using the compiler's located evidence. Proven old findings stay nonblocking and `unverified`; report them without automatically widening scope or rewriting callbacks/types. New occurrences, changed declarations and newly reachable bad references block. Syntax, native signatures, exact generation and complete C# checks remain mandatory. Explicit user acceptance rules still apply even if the baseline fails them. Read the compiler contract before interpreting such findings; never change generation mode to evade a check.
- Preserve exact target ownership, draft concurrency, account/index gates, pinned grant fingerprints, one affected row per statement and signed human approval. Prefer least privilege; never select `shared_unrestricted` without the user's explicit local configuration confirmation.
- Never approve/execute for the human, bypass expired/tampered approval, clear a live executor, call backend save/publish endpoints, connect Redis or write/delete DLL/PDB. Cancellation and local release require the dedicated inspected scope and explicit user agreement described in session workflows; they are not automatic cleanup. Restore is a new approval transaction. Uncertain outcomes need recovery or confirmed local release retaining its unverified result and audit history.
