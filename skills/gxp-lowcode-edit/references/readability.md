# 保留真实变量与原生显示的可读编排

维护者应能从画布对应到真实变量、取值、判断和调用。保留原生生成的说明格式，通过有意义的变量和清楚的子动作组织逻辑。直接在原有规划中完成，不增加审批回合、工具调用、重复编译或评分门禁。

## 显示真实变量和取值

原生 `convertToHtml` 会优先用参数对象的 `label` 生成画布说明。不要通过修改它把真实变量或表达式替换成中文业务概述。

- 自定义变量引用和取值沿用实际标识及原生显示。新建自定义参数时，`value`、`code`、`label` 使用同一个真实变量、常量或表达式，不把 `sourceMaintenanceContext` 显示成“本次来源维护步骤上下文”，也不把 `true` 显示成“是”。
- 定义变量应能读到实际变量名和实际初值，例如“定义 字符串 变量 variableName 的值为 1”。`learningPlanRows[0]` 保持可见，不替换成中文概述。
- 以上适用于自定义值。原生选择器生成的字段、组件、模型和动作引用保留原有标识、标签、链接及类型，不将引用记录改成自定义文本，不强行让这些记录的 `label/value/code` 相等。
- 新变量采用与职责一致、便于检索的名称，例如 `shouldBindQualification`、`sourceMaintenanceContext`、`affectedPeriodicIds`。现有变量沿用真实名称，不为显示而改名或影响外部绑定。
- 中文业务解释放在必要的原生注释、分组说明和参数说明里作为补充，不能覆盖变量名、实际取值和原生节点说明。分组仍可使用明确的业务名称。

## 原生步骤优先，变量只承载必要计算

先按真实元件契约选择节点：查询用查询元件，分支用原生条件，子动作调用用 `CallAction`，字段赋值用对应赋值元件。原生能力能等价表达时，不把请求、调用、写入、批量回填或整个业务步骤包装成 `SetVariable` 初值；`result = imbiz.setValues(...)` 仍是在变量节点中隐藏副作用。

- IF 优先用原生 `condition.Filters` 的目标、比较、值与 AND/OR 结构展示判断，保留短路与原求值顺序；不能证明等价时不强行展开。
- 对本次新建或修改的表达式都应用可读性规则，不只在用户明确要求“重构”时应用。仅对有实际含义、需要复用或原生条件无法清楚表达的纯计算定义局部变量，再在原位置引用。不能把一个巨大表达式搬进变量就声称已经可读，也不把每个简单比较拆成变量。
- 变量初值若同时揉合业务分支和集合筛选/聚合（例如嵌套三元再接 `Where`、`Select`、`OrderBy`、`Max` 或 `Any`），不要把整段当作“必要纯计算”留在一个“定义变量”节点。先用可见的 `IfCondition` / `ElseIfCondition` 分出业务路径，在各分支内保留单一用途的取值、筛选或聚合，并保持原默认值、求值时机和无匹配行为。单一且语义清楚的筛选或聚合可以保留表达式；不把 LINQ 机械展开成循环，不为每个比较定义变量，不因显示新增子动作。若当前原生元件无法等价表达，保留必要表达式并在交付中明确指出它仍需读代码，不能称为画布上已可读。
- 大量字段映射应保留来源和目标可核对的原生映射；无法等价表达时保留既有映射并说明位置，不新增 `Object.fromEntries`、IIFE 或长三元表达式压缩整段业务。
- 框架方法、异步返回与输出参数必须有当前元件或源码契约依据，不凭名称猜 API。读取已确认的精确实现即可，不为此重扫整条业务链。

### 放在正确的计算位置

- 定义放在原判断所在路径、输入就绪之后、使用之前；依赖循环项的判断在循环体内逐轮计算，不能提到循环外后使用旧值。
- 原本只在父分支或锁内执行的表达式，定义仍留在同一分支或锁内。整段 OR/AND 表达式移入一个变量时保持短路关系，不提前分别求值所有子条件。
- FOR 的复杂集合表达式先使用明确命名的集合变量，再让循环引用它；保留原来的延迟求值、迭代顺序和状态更新，不擅自加 `.ToList()` 改成快照。
- for/while 退出条件依赖循环体更新的数据时，保持原求值频率，在原求值位置刷新变量或使用仍会重新求值的原生条件；覆盖 `continue` 路径，不能只在可能被跳过的循环末尾更新，也不能缓存首次计算的布尔值。不能证明等价时，先保留原生动态条件并说明待处理边界。
- 简单变量、常量和原生比较不再套一层无意义变量。临时变量不共享到全局，不新增查询、循环或调用来美化显示。
- 既有中文别名需要纠正时，从真实参数的变量标识和执行值恢复显示，不从中文概述反推代码。

## 主动作表达流程，子动作承担业务步骤

有多个独立业务分支、重复的完整处理步骤，或主线中混杂大量查询、计算和写入细节时，优先提取子动作。简单、连续的一小段流程不必强拆；不设按节点数量拆分的硬阈值。

- 主动作保留入口解析、必要校验、分派、共享的事务或锁，以及最终返回；具体职责明确的步骤通过原生 `CallAction` 调用子动作。
- 按业务职责命名，例如“解析学习来源”“登记学习来源”“绑定资格来源”“解除来源关联”“结算受影响的周期培训”；避免“处理1”“子动作A”“执行逻辑”。这些名称是示例，实际以当前规则和完整处理范围为准。
- 用 `group_description` 说明子动作做什么、从哪里获得输入、返回什么，以及异常由谁处理；声明参数使用原生说明字段。新局部变量按业务对象命名，不沿用 `temp1`、`obj2`、`flag3` 之类临时占位名。
- 提取完整闭合的条件、循环和异常处理块，显式传入依赖并返回结果。保留原有输出字段、默认值、异常、锁覆盖范围、事务边界和数据写入顺序；不要把子动作移到原锁之外，或让主动作提前返回而漏掉后续步骤。
- 共享状态不能靠新增隐式全局变量拼接。先依据真实调用契约和变量使用确认参数，不将代码片段随意搬到其他分组，也不拆成必须来回跳转才看得懂的碎片。
- 单个巨大 IF、深层嵌套、重复的同类校验和长拼接表达式，应结合职责重新组织；仅修改名称或加一句注释不算完成结构改善。

## 拆分不扩大业务范围

用户要求拆分或整理可读性时，原样提取已有闭合步骤及其必要输入输出；只调整声明、调用、引用和原段替换。保留条件、数据来源、模板映射、去重、并发、异常和执行顺序，不顺手重写或追加防御规则，不复制上游计算或副作用到多个子动作。

优先在同一完整候选中完成提取、接线、原段替换与重复入口清理。新子动作通过 [同批 CallAction 别名与参数绑定](patch-schema.md#同批调用新建子动作) 接入，不为取得生成编号而先保存空壳。技术限制确需分次保存时，事先说明每批是否接通、剩余工作及完整交付条件；中间批次保存不能称为本次功能已完成。

## 注释解释必要的业务原因

使用已支持的原生 `CustomExt` 注释元件，在重要阶段入口或不直观的规则前简短说明原因、适用范围和异常去向。它通过普通 `append_node` / `insert_before` / `insert_in_block` 创建，内容在 `input_params.content`，不需要新增工具或手写节点 `title/description`。

注释用于补充规则依据，不逐节点重复“定义变量”“执行查询”。原生生成器将内容放到单行 `//` 注释后，因此每个内容使用单行文字；多段说明分成必要的原生注释节点，不夹带可执行片段。

## 利用当前候选完成一次自查

沿已有候选和差异读一遍：维护者能否直接找到入口、命中条件、写入位置和异常出口；主动作是否呈现业务步骤；子动作是否能独立说明输入和结果。复用已有生成及复核证据，不为可读性再加一轮生成、编译、评分门禁或固定数量限制。

交付时用简短的主线和子动作职责说明改动位置，业务规则以实际参数为准。只有只读证据时，将具体拆分描述为方案，不声称已经修改了业务草稿。
